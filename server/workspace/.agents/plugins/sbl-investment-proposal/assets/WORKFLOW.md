# 德塔式证据驱动投资提案智能体工作流

本流程固定“正式投资提案的文体与版面”，不固定任何样本公司事实。当前 Claude Code 模型负责抽取、裁决、分析与写作；`deta_ic_processor.py` 只负责材料解析、输入锁定、硬门禁、模板污染检查、渲染和审计，不调用外部大模型网关。后台保留完整事实库、冲突裁决、预测和质检记录，正式成稿只呈现自然、连贯、可直接审议的读者版内容。

## 阶段门

| 阶段 | 目标输出 | 通过条件 | 失败后的订正目标 |
|---|---|---|---|
| G0 实体与决策锁定 | `workflow_state.json`、`entity_binding` | 用户确认的投资主体全称/简称、目标主体、禁用旧主体、基准日、币种、轮次、输出格式明确 | 停止写作，先消除管理机构、基金、执行主体和目标主体的身份歧义 |
| G1 来源盘点 | `source_manifest.json`、`packets/` | 关键材料解析失败数为 0；来源版本、日期、哈希可追踪 | 修复解析、补 OCR、去重与版本裁决 |
| G2 事实与冲突 | `facts.json`、`rulings.json` | 重大数字含主体、单位、期间、口径、来源；冲突已裁决或显式保留 | 降调、补证或生成尽调问题 |
| G3 投资主线 | `investment_thesis_tree.json` | 每条主线均有机制、事实、里程碑、反证和资本含义 | 删除宣传主线，补齐因果链断点 |
| G4 八通道分析 | 财务、商业、交易、预测和风险底稿 | 客户阶段不混用；历史财务和预测可复核；估值、持股及条款勾稽 | 重算、分期、折价、终止触发 |
| G5 正文计划 | `section_coverage.json`、`proposal.json` | 六章完整；材料支持的事实维度已经展开；正式叙事；不暴露内部底稿、事实 ID、评分或审计过程 | 补足遗漏事实维度、删除工作痕迹与重复信息 |
| G6 自动质检 | `qc_report.json` | 结构、算术、来源、黑名单、必覆盖项全部通过 | 定向修改底层事实或模型，不只改措辞 |
| G7 独立红队 | `red_team.json`、`revision_log.json` | 以“不投资”为默认假设；P0/P1 全部关闭 | 改估值、持股、分期、条件或结论 |
| G8 评分 | `quality_scorecard.json` | 总分≥85；证据/数据/因果/财务单项≥60%；硬门禁全通过 | 按最低分维度订正，禁止无关扩写刷分 |
| G9 模板与视觉验收 | DOCX、成品清单、全页 PNG、PDF | 批准模板哈希一致；`template_enforced=true`；`renderer_mode=clone-approved-docx`；无截断、重叠、乱码、不可读表格、样本残留或错误页码 | 恢复批准模板，调整表宽、分页、字体和内容容量后重渲染 |

## 固定视觉规范

- 页面沿用16.2cm×21.0cm小开本，页边距上、下均为1.5cm，左、右均为1.8cm。
- 主标题使用黑体17pt、加粗、居中；标题块段前12pt、两行间距6pt、段后18pt。
- 一级标题使用黑体14pt、加粗、左对齐，段前12pt、段后6pt。
- 二级标题使用黑体12pt、加粗、左对齐，段前8pt、段后4pt。
- 正文使用宋体10.5pt，首行缩进2字符，1.4倍行距，段后3.5pt。
- 表格正文使用宋体9–9.5pt；表头使用黑体9.5pt、加粗、浅灰底；表宽必须收敛到左右1.8cm页边距形成的版心内，不得越界或裁切。利润表与“营业收入五年预测”表必须采用完全一致的字号：表头黑体9.5pt、正文宋体9pt，禁止预测表以缩小字号换取单页容纳。
- 表格单元格不得继承正文首行缩进；落款主体与日期必须成组排版，不得出现仅有日期的空白末页。
- 所有正式DOCX必须在Word原生渲染后逐页检查；发现标题换行失控、表格过宽、字体替换、文字截断或异常分页时不得发布。
- 正式DOCX必须从批准的V7模板克隆生成，不得从空白 `Document()` 开始。批准模板SHA-256固定为`849a6e1ec86c9576f52332ffbf8dc048dea5d929daa438810f701c4e2116da15`；模板缺失、哈希漂移或成品清单未记录模板来源时必须停止。

## 事实与写作规则

1. 用户明确确认的投资主体身份具有最高优先级。起草前必须建立 `entity_binding`，至少登记 `investment_entity_full_name`、`investment_entity_short_name`、`target_entity_full_name` 和 `forbidden_investment_entities`；标题、导语、交易条件、治理权利、投资亮点、结论（如出现主体）及落款必须使用同一绑定。不得从旧报告、样本、文件名、协议签约方或历史基金名称推断本次投资主体。
2. 管理机构、基金、有限合伙人和执行主体仅在用户明确确认其角色不同时区分；未明确确认不同执行主体时，落款和执行主体均使用投资主体全称/简称。正式版发布前必须扫描并清除 `forbidden_investment_entities` 中的旧主体和冲突简称。
3. 后台始终区分已确认事实、待确认信息和分析判断；除“六、结论”按本流程形成投决判断外，正式提案各章节仅呈现用户提供且已经确认的客观事实。
4. 后台始终区分线索、测试、PoC、合同、验收、收入、回款与复购；客户合同、流水、权属清单等证据材料不进入正式提案。
5. 技术强主张必须绑定测试集、样本、基线、指标、日期、第三方复核和 IP 归属。
6. 历史财务不补零、不插值；预测采用数量×单价×换算系数等业务驱动。
7. 仅在用户明确提供投资结论时按原意呈现金额、估值、目标持股及交易条件；用户未提供时不得自行生成投资建议、条件或结论。
8. 样本报告只提供结构、语气与视觉系统，禁止复制样本公司名称、人物、客户、数字和结论。
9. 除“六、结论”外，正文各章节只客观描述用户提供的事实、业务情况、行业风险及公司应对措施，不写主观评价、价值判断、成功关键、依赖条件、额外机制解释或投资含义。结论仅在用户已有明确投资建议时形成有依据的投决判断。
10. 数据颗粒度优先落实到明确主体、报告期、单位、业务或会计科目、金额/数量和判断边界；避免只有比例、形容词或结论而无基础数据。
11. 正式版不展示投资回报测算，不出现 MOIC、IRR 或退出价值敏感性表；相关测算如需保留，仅存在后台模型中。
12. 正式版仅保留完整资产负债表、完整利润表及必要的公司业务预测；删除“补充经营与单位经济性指标”和“现金流量表（摘要）”。
13. 资产负债表使用“资产｜期末余额｜负债和所有者权益｜期末余额”，利润表使用“项目｜本年累计金额｜本期金额”，并列全标准科目；不得用摘要表替代。
14. 表格下方不得追加口径说明、审计提示或投资判断；期间与单位放在表题上方，分析内容进入前置正式段落或相应业务章节。
15. “四、公司业务预测”从新页开始，标题后不得放置说明段落，必须直接进入题为“营 业 收 ⼊ 五 年 预 测”的完整预测表，不得将业务分组拆到下一页；该表使用“营业收入（税前）构成｜连续五个预测年度”表头，并按业务分组，每个业务固定列示业务收入、销售数量（写明项目/万小时等单位）、平均单价（元）、平均成本（元）和毛利率。
16. 风险控制统一写成简洁的“风险—应对措施”，仅使用用户提供的行业风险和公司现有应对措施；不得自行设计制度、交易条件或控制动作，不写核查过程或证据索引。
17. 正式提案禁用“项目组、专项核查、管理层列示、不同材料、投资团队”等来源标签，也不得出现销售合同、银行流水、权属清单等证据载体；“项目组认为”仅可作为“六、结论”的投决主语使用。
18. 禁止使用“投资意向书要求、本意向书要求、投资方要求、协议要求、本文件要求”等引用外部文件的话术，也不得自行补充“要求公司建立/完善某项制度”或“使某事项具备稳定边界”等语句。
19. 正文禁止出现“该路径能否形成持续价值，主要取决于……”“成功关键在于……”“有望……”等评价、推测或依赖分析；“投资价值”类判断仅可出现在“六、结论”，并须由正文事实与交易条件支撑。
20. 每个预测年度的业务收入必须由销售数量×平均单价及计量单位换算系数重算；毛利率必须由（平均单价－平均成本）÷平均单价复核。任一业务缺少四项驱动或算术不一致，禁止生成正式版。
21. 正文扩充以事实维度为单位，不以最低字数为单位。公司简介、核心团队、股权结构、技术路线、运营摘要和投资亮点必须先建立 `section_coverage.json`，记录材料可用维度、正文已用维度、段落数和材料缺口。
22. 公司简介按主体身份、办公布局、业务定位、产品服务、服务对象和经营形态展开；主体身份可写公司名称、成立时间、注册资本、法定代表人和注册地址，但正式提案不呈现统一社会信用代码或18位信用代码。核心团队按总体构成、创始人、运营/产业人员、技术专家及职能配置展开；股权结构按截至日、当前股东、控制关系及融资沿革展开。
23. 技术路线采用“一段总体架构＋每个已确认模块一段”，每个模块从输入、方法、输出、指标、场景和当前状态中选用已有事实。明确区分已形成、已交付、正在工程化、在研和规划。
24. 运营摘要区分接触、测试、PoC、合同、交付、验收、收入、回款和复购。投资亮点用四至六项相互独立的客观事实归纳，不以“唯一、领先、壁垒、成长性、投资价值”等评价词代替事实。
25. 当材料支持的事实维度达到章节门槛时，正文必须充分展开；材料不足时在后台记录 `missing_dimensions` 并保持精炼，不得使用常识或推断补齐。
26. “六、结论”在 `section_coverage.json` 中登记 `decision_mode`。推荐模式采用一个段落，按“综合考虑赛道窗口、技术路径及壁垒、商业验证、团队、综合入股估值/折让、下行保护—项目组判断—充分控制风险下按主方案实施”组织；每个分句必须映射到已确认事实，无依据即删除或降调。结论覆盖矩阵只使用 `赛道窗口`、`技术路径及壁垒`、`商业化验证`、`团队构成`、`综合入股估值或价格折让`、`下行保护`、`主方案` 七个标准键；推荐模式至少使用四项并必须包含 `主方案`。

## 原文润色模式

当输入包含一份已有投资提案并要求润色、扩充、优化、改写或完善时，启用原文润色模式：

1. 原文与用户补充信息是唯一内容边界。允许增加非实质性的逻辑衔接、明确主语和专业表达，不得增加新事实、新数据、新预测、新结论、行业对比或未来展望。
2. 在改写前保存只读原文，并生成逐句事实对应关系及章节事实覆盖矩阵；任何新增句子无法对应原文或补充信息时必须删除。
3. 财务章节整体锁定。资产负债表、利润表及所有财务文字、标题、表头、科目、金额、期间、单位、顺序和格式必须与原文完全一致，不得润色、补充、删减、重排或重算。
4. 公司简介、股权结构、技术路线、交易条件、业务预测、投资亮点、风险控制和结论可在事实边界内适度扩充；采用“总体定义—构成拆解—实现方式—量化信息—当前状态”展开已有事实；信息不足时保持精炼，不使用常识、公开信息、模板内容或推断补齐。
5. 除结论外，正文只客观描述事实、业务情况、行业风险和公司已有应对措施，不增加主观评价、价值判断、成功关键、依赖条件、额外分析或推测。结论可按原文明确建议形成投决判断，但不得添加原文没有的依据。
6. 完稿后先执行财务原文一致性比较，再执行章节覆盖、结论依据映射、评价性语言和新增事实扫描；任一失败均不得发布。

## 评分与订正

评分采用 100 分制：决策清晰度 10、证据可追溯 15、数据颗粒度 15、因果深度 15、商业验证 10、财务与预测 15、交易与条款 10、风险控制 5、正式文风与视觉 5。每次订正必须记录 `issue_id、优先级、原结论、问题、影响、修改、证据/重算、复核结果、状态`，但评分和订正记录不得写入正式提案。

P0 可能改变投/不投、价格、持股、回报或合法性；P1 影响主线可信度、预测或关键风险；P2 为结构与视觉；P3 为措辞。P0/P1 未关闭时不得生成正式版。

## CLI

```bash
python deta_ic_processor.py init \
  --input /abs/project.zip \
  --reference /abs/德塔智能投资提案.pdf

python deta_ic_processor.py audit --artifacts /abs/run-artifacts

python deta_ic_processor.py render \
  --artifacts /abs/run-artifacts \
  --template /abs/plugin/assets/德塔式精简工商字段投资提案_固定模板V7.docx \
  --output /abs/目标公司投资提案.docx

python deta_ic_processor.py verify \
  --docx /abs/目标公司投资提案.docx \
  --output-dir /abs/qa --word-native
```

macOS 上优先使用 `--word-native`，脚本持有明确的 Word 文档对象，避免活动文档竞争；无 Word 环境再使用默认 LibreOffice 渲染器。
