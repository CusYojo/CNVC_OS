# 公开信息交叉核验规范

## 目标和边界

将公开检索作为本地尽调材料的交叉核验和风险发现层，不作为基金协议、交易安排、未公开财务数据或正式交易文件的替代证据。默认对每个可交付合规性说明执行受控公开核验；用户明确要求离线，或客观无联网能力时，仍生成一份记录限制的离线核验文件，不得静默跳过。

公开信息只能支持“截至查询日，在列明公开渠道未发现……”或具体已核实事实。搜索无结果不等于事项不存在，普通搜索摘要不等于官方记录。

## 查询输入与保密边界

仅使用已经公开或适合公开检索的主体标识：

- 企业全称、统一社会信用代码、历史名称、注册地址、法定代表人；
- 需要核查的主要股东、实际控制人、董事和关键关联主体姓名；
- 公开产品、专利、商标、许可证或备案名称。

不得把基金名称与未公开项目组合、拟投资金额、估值、老股安排、返投缺口、投委会意见、基金协议条款、保密交易结构或客户未公开数据写入查询词。将查询词和主动排除的敏感主题记录在`scope`中。

## 主体消歧

先确认主体，再评价风险。目标公司至少使用企业全称与统一社会信用代码匹配；自然人和关联企业需同时匹配两个以上标识，例如姓名加任职公司、姓名加公开职务。无法唯一匹配时标记`identity_unresolved`，不得将结果用于“未发现风险”的决定性结论。

## 来源顺序

1. 国家和地方政府、司法机关、监管机构、知识产权机关的直接页面或正式文件；
2. 公司官网、正式公告和可验证备案页面；
3. 可靠媒体的原始报道；
4. 商业数据库；
5. 搜索引擎结果页和摘要，仅作为发现线索。

搜索结果页、聚合摘要、转载和缓存片段不得作为直接证据。每条直接来源记录标题、发布者、URL、访问日期、匹配标识和简短的非侵权事实摘要。

## 默认核验范围

每个在线项目至少覆盖七类：

1. `corporate_registration`：登记状态、法定代表人、注册地和主体一致性；
2. `administrative_penalties`：行政处罚、经营异常和严重违法失信；
3. `credit_and_enforcement`：公开信用、被执行和失信被执行信息；
4. `litigation`：可访问司法公开渠道中的重大诉讼或裁判线索；
5. `intellectual_property`：核心专利、商标或公开知识产权主体一致性；
6. `licences_and_filings`：与业务有关的许可、网站或行业备案；
7. `public_adverse_information`：公司及关键人员的重大公开负面线索。

网站不可访问、验证码阻断、公开库覆盖有限或信息可能滞后时，标记`access_limited`并说明限制。不得为了达到“通过”而将受限查询改写成已核验无风险。

## 冲突和结论门禁

- 内部材料与公开信息不一致时，保留两套口径、来源、时点和适用定义；不得静默选择更有利版本。
- 可能反转主体资格、股权、处罚、重大诉讼、知识产权权属或投资结论的冲突标为`material`。
- 未解决的重大冲突阻止生成可交付DOCX。
- 非重大或时点差异可在审计层解释，并把必要条件集中到`open_issues`或最终条件性结论。
- 正文仍保持Deta式简洁。公开核验详情放入`public_verification.json`，正文最多在第七项或相关事实处用一句“截至查询日，在列明公开渠道未发现……”承接。

## 文件和校验

按`public-verification-schema.json`生成`public_verification.json`，再运行：

```bash
python scripts/validate_public_verification.py public_verification.json --out public_verification_validation.json
```

只有结构校验通过、主体已消歧、查询日期存在、来源可追溯、限制已披露且无未解决重大冲突时，才可把`summary.validation_status`设为`pass`。`coverage_status`可以是`limited`，但必须与限制说明一致；结构通过不等于公开渠道覆盖完整，也不等于目标公司绝对不存在风险。
