# 合规性说明 Reviewer、Formatter 与兼容验收

## 1. Content Reviewer

以下检查用于在进入 Formatter 前清除不安全内容。联网、模型或内容 Reviewer 异常不得直接终止任务；未通过项必须删除、留空或替换为可追溯的资料边界后再进入 Formatter。

### 1.1 结构

- 标题严格为 `关于{项目简称}项目投资合规性的说明`。
- 八个逻辑槽名称、数量和顺序正确。
- `公司情况介绍` 只作容器，findings 为空。
- 公司简介、核心团队、产品及技术完整。
- 投资理由恰好五项。
- 投资情形分析恰好七项且顺序固定。
- 结论恰好一项，包含明确的成立条件且不显示为版面标题；不检查固定开头。

### 1.2 证据与幻觉

- 除程序性结论外，`资料记载`、`AI推断` 和 `待核验` 至少引用一条有效证据。
- 引用与 finding 的主体、数字、专名和判断直接对应。
- `资料缺口` 不带来源，并明确本项核查对象、待取得的具体材料和形成结论的完成条件。
- 正文不得出现 `当前项目暂无相关资料。` 或跨章节连续复制的统一缺口占位语。
- 正文不得出现“现有项目材料显示”“交流纪要记载”“根据当前项目资料”“项目档案显示”“公开资料可提供”等来源或取证过程。来源名称、文件类型、证据状态和检索路径只保留在 `sourceIndexes`、产物元数据与审计侧车中；finding 必须直接陈述消化后的事实、判断和具体核验条件。
- 不出现非当前项目的主体、人员、数字、日期或交易条款。
- 不虚构法规、许可、审批、基金条款、返投、关联关系、集中度、估值、金额或比例。
- 不把预测、意向、访谈或主体自述写成已交付、已签约或已回款事实。
- 除非用户明确要求只联网搜索，审计记录必须证明已按“本地项目资料库 → 网络缓存 → 项目大模型定向网络补全”的顺序取证，不得一开始就进行宽泛的全网搜索。
- 网络补全必须使用项目统一大模型网关、当前任务模型或既有 Agent 联网能力；不得由本 Skill 单独调用搜索引擎、第三方搜索 API 或抓取服务。
- 网络缓存和新获取的公开补全来源必须保留页面标题、规范化 URL、发布主体、发布日期或更新时间、访问时间、内容指纹、项目大模型名称和统一网关调用标识；新获取的有效结果必须已写回当前项目缓存。
- 普通模型对话、训练记忆、无 URL 结论或模型自行生成的网址不得作为联网结果；模型没有真实联网与来源引用能力时必须报告能力不可用。
- 只引用网络缓存或新获取公开材料的 finding 必须标记为 `待核验`。
- 网络补全与本地原始记录冲突时必须并列披露并标记 `待核验`，不得覆盖本地证据。
- 对公开可查事项，在没有项目大模型网络补全审计记录时不得输出资料全空结论。
- 公开监管规则、基金公告、返投认定文件、返投公示或公开投资记录必须用于形成 `待核验` 的初步核查；不得据此声称本基金内部余额、完整台账或本次交易已经满足限制。
- 已取得相关公开依据的核查项不得整体退回资料全空结论；只能在同一 finding 中说明尚未公开的具体内部数字或交易细节。

### 1.3 一致性与数字

- 同一事实、数字、风险或缺口不跨章节重复完整表述。
- 投前估值、投后估值、融资额、投资额和持股比例口径一致。
- 基金出资、共同投资、SPV 总额和风险敞口不混写。
- 返投和集中度写明基准日、分母、计算过程和比较结果。
- 数字冲突时不自行修正。
- 存在待核验或资料缺口时不使用无保留合规结论。

### 1.4 叙述风格

- 先陈述主体、时间、动作、金额、比例和状态，再写必要判断；不得以抽象价值标签替代事实。
- 不使用“具备初步判断依据”“可形成初步投资判断”“已有商业化线索”“具备一定交付组织基础”“客户验证已出现多场景线索”等模板化概括。
- 出现“关键核验对象”“关键核验条件”“核验条件尚未闭环”“条件性分析”“条件化判断”“取证边界”“核验边界”“形成单项结论”“完成专项分析”“本节需取得”等内部流程用语，返回 `AI_STYLE_DRIFT`。
- 不自行命名“平台化……加场景化……”等概念，不使用“支撑强度”“成长路径”“利润留存能力”等脱离具体事实的抽象名词。
- 三段以上连续以“……方面，……”开头，或两段以上连续使用“最终结论取决于……”收尾，返回 `AI_STYLE_DRIFT`。
- “仍需核验”“尚待明确”“以……为准”必须对应具体事项；不得作为每段固定尾句。
- 每段只围绕一个逻辑中心，避免在同一句连续堆叠三个以上抽象判断。

### 1.5 正文边界

- 不增加封面、执行摘要、责任声明、风险提示、资料缺口或引用资料正文板块。
- 不显示状态标签、`[S#]`、模板路径、Skill 名称或生成引擎。
- 审计元数据不混入正文。
- 项目资料、会议或访谈纪要、项目档案、网络检索等来源过程不进入正文。
- 不出现 Markdown 星号、井号、代码围栏或 HTML 标签。
- 不出现 PDF/PPT 页码、目录、页眉页脚、孤立章节编号或多个目录项粘成一行的文本；`39 06丨机会与风险总结`、`目录……公司介绍……融资发展 02 03 04` 等内容必须删除，不得当作业务事实。
- 标准英文/数字词保持连续：`AI-Core-Tech`、`COO`、`CEO`、`4D` 等不得出现 `AI- Core- Tech`、`C OO`、`4 D` 一类断词。
- 核心团队必须一名成员一段，并以清楚的姓名—职务关系开头；成员段少于必要履历信息、混写多名成员，或混入页眉、公司名、专利数量和下一页内容时返回 `TEAM_STRUCTURE_INVALID`。
- 产品及技术必须一项产品或技术能力一段，写清名称、机制、明确指标或验证及应用价值；出现“名称类别关联度”、连续预测表字段、残缺专利行或多个页面粘连时返回 `PRODUCT_STRUCTURE_INVALID` 或 `SOURCE_LAYOUT_FRAGMENT`。
- 每个 finding 必须以完整中文句号、问号或感叹号结束；缺少句末标点时返回 `MISSING_TERMINAL_PUNCTUATION`。
- `1 0%`、`4 000万`、`3 0人` 等同一数字被拆开时必须在单位明确的前提下还原；“方案方面”“估值口径方面”“营收方面”等机械标签返回 `AI_STYLE_DRIFT`。

## 3. Formatter

Formatter 只消费审核通过的 JSON 和 Blueprint，不重新创作业务内容。

### 3.1 Word 版式

- A4 纵向，单节，左右 1800 DXA、上下 1440 DXA。
- 无可见页眉、页脚、页码、目录、表格、图片或浮动对象。
- 标题为黑体 14 pt、常规、居中、1.5 倍行距。
- 一级标题为宋体 12 pt、加粗、段前 12 pt。
- 二级标题为宋体 12 pt、加粗；正文为宋体 12 pt；均为 1.5 倍行距。
- 一级标题必须显式清除字符首行缩进；二级标题必须显式设置左缩进 0 DXA、首行缩进 482 DXA，禁止由 `List Paragraph` 默认样式叠加缩进。
- 所有正文段落均两端对齐、左右缩进为 0、首行缩进约 480 DXA、段前后为 0；核心团队和产品及技术不得例外取消首行缩进。
- 理由、投资计划和核查内容均使用连续正文段落、首行缩进约 480 DXA，全段常规字形。
- 核心团队与产品技术按成员/能力分段；可仅将段首“姓名（职务）”或产品/技术名称加粗，其余正文保持宋体 12 pt 常规字形，不使用表格或卡片替代公文正文。
- 正文不得出现数字小标题或“学术团队：”“业务主体：”“投资方式及投资限制：”等标签式开头。
- 落款和日期右对齐。

### 3.2 编号

- 一级标题显示 `一、` 至 `四、`。
- 二级标题显示 `（1）` 至 `（3）`。
- 仅一级、二级正式章节使用合法 Word 编号定义。
- 投资理由和投资情形分析不显示阿拉伯数字编号，不把标号写成手工文本、Markdown 星号或 Unicode 圆点。

### 3.3 分页

- 标题与首章不形成异常大空隙。
- 一级、二级标题不孤立在页尾。
- 落款和日期不拆页。
- 不出现仅剩少量文字的异常空白尾页。
- 不通过缩小字号或压缩行距控制页数。

## 4. Word Reviewer

检查：

- DOCX 为有效 OpenXML ZIP，所有 XML 可解析。
- `[Content_Types].xml`、关系、样式、字体和编号引用闭包完整。
- 不存在悬空关系、重复 ID、无效编号引用或 U+FFFD。
- 标题、四章、三个子节、五项理由、七项核查、结论和落款完整。
- 页面、边距、字体、字号、行距、缩进和编号符合 Blueprint。
- 无多余正文板块和非本项目事实泄漏。
- 无模型化套话、相同句式连用或机械重复的核验尾句。
- 无 Markdown、来源页码/目录残片或被空格拆开的英文缩写和数字词。

失败时修复 Formatter 并重新生成一次；仍无法生成可由 Word/WPS 正常打开且无乱码的 DOCX 时，才按基础设施异常停止，不得交付损坏文件。

## 5. Microsoft Word / WPS 兼容验收

在应用可用时分别打开最终 DOCX，检查：

1. 不出现“发现无法读取的内容”、修复、恢复或另存为新文档提示。
2. 中文无乱码、方框字或字体替换。
3. Word/WPS 字体栏能识别标题黑体 14 pt、正文宋体 12 pt。
4. 一级、二级标题均为宋体 12 pt 加粗，编号未因 `List Paragraph` 字符首行缩进整体右移；正文不出现数字小标题、加粗引导语或冒号标签。
5. 页面没有文字重叠、裁切、孤立标题或异常空白尾页。
6. 落款与日期完整且右对齐。

出现任一问题即返回：

- `WORD_REPAIR_REQUIRED`
- `WPS_REPAIR_REQUIRED`
- `FONT_MISMATCH`
- `NUMBERING_INVALID`
- `EMPTY_TAIL_PAGE`
- `LAYOUT_OVERFLOW`

不得交付需要恢复才能打开的文件。

## 6. 单一交付物

只允许登记并交付一份通过 Word/WPS 结构与编码安全检查的可编辑 DOCX。内容 Reviewer 的剩余问题必须先通过删除、留空或资料边界替换消除；出现 PDF、Markdown、PPT、PPTX、图片或其他伴生产物时，删除伴生产物并保留 DOCX，不把整项任务标记为失败。
