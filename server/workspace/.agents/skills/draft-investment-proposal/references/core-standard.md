# 投资提案核心规范

本文件是 `docs/投资提案模板分析/投资提案模板核心规范.md` 的运行时执行摘要。源文件 SHA-256：
`ee3fdb2ebb9b2f67f254334be4e9d85a2d66141e3786b4e56df53602d0a47ee5`。

## 权威边界

- 角色定位为投资中台资深投资经理；输出是供投资团队、投资总监和投委会审阅的内部投资提案，结论必须说明投资价值、成立条件、交易约束、主要风险和下一步实质工作，不得用系统内部项目阶段枚举代替分析。
- 只处理当前会话绑定的 `projectId`。项目摘要、标签、评分和融资摘要只能作为内部候选信息，不得借用其他项目资料或自动升级为已核验事实；客户可见正文不写内部项目状态、OA、系统按钮或技术流程。
- 核心规范决定稳定结构、版式、写作和章节任务。
- 九份模板用于验证共同规律、学习书面语和表格形态。
- 单份模板中的封面、目录、扩展小节、字号差异和项目事实不进入核心规则。
- 默认取证顺序：当前项目资料库原始文件与授权证据 > 项目结构化字段 > 用户本次明确输入 > 当前项目网络补全缓存 > 本次定向网络补全 > 基于证据的审慎分析 > 模板仅供结构与风格参考。
- 默认先检索本地资料，再复用网络补全缓存，只对影响项目判断的具体缺口进行定向网络补全；除非用户明确要求只联网搜索，不得一开始就进行宽泛的全网搜索。
- 不恢复或依赖 SearXNG；有效网络补全结果写回当前项目缓存，公开网页证据一律只作为`待核验`线索，不能替代一手交易、工商、合同或财务文件。
- 最终只生成、登记并交付一份可编辑 DOCX，不生成或登记 PDF、Markdown、PPT/PPTX 或预览产物。

## 内容构成

开篇依次为：主标题、`各位投资决策委员会成员：`、项目提案说明、审议授权边界。

正文为六个一级章、十一个二级节，共 17 个节点；前三个一级章仅作容器，第四至第六一级章直接承载正文。14 个叶子章节必须逐节生成。

结尾依次为：条件式结论、机构落款、日期。正文末尾不增加`免责声明`或`引用资料`板块。

## 写作范式

- 不写泛行业研究；每段必须围绕当前项目的主体、股权与治理、团队、产品与技术、市场与客户、商业模式、财务、融资与估值、交易方案或风险。
- 一个 finding 对应一个完整、连续的正文段落，段内不得使用手动换行。事实章节直接写主体与事实，必要判断放在段末；风险和结论章节可以先给判断，再说明依据、影响、约束和动作。不得逐段套用`判断：`、`依据：`、`影响/约束：`、`待办：`等底稿标签，不得使用`1、`、`（1）`、`一）`等数字小标题，也不得把多个`标签：值`字段串在同一段。固定章、节标题不属于正文 finding。
- 参考九份模板的共同文风，优先以公司、人员、产品、客户、合同、投资方或交易安排为主语，直接陈述具体事实。段落数量、句数和长短由证据密度决定，通常用一至四句讲清一个中心意思；不强迫每段套用同一分析框架，不复述章节任务，不连续堆叠`具备`、`形成`、`构建`、`依托`、`有望`、`进一步`等泛化动词。
- 公司简介按主体、成立时间、所在地和业务定位展开；团队按姓名、职务、经历和职责展开；产品技术按名称、功能、技术组成和产品化进度展开；运营按客户、订单、交付、回款和渠道展开；交易按金额、估值、股比、资金用途和保护条件展开。风险和结论才集中写条件、影响、动作和流转边界，事实章节不机械追加推进建议。
- 访谈、聊天记录和会议转录必须先转写为正式事实，不直接保留`但是其实`、`然后就是`、`差不多`、`各种尝试`、`接下来是`、`我觉得`、`我们这边`、`说白了`等口语；不得用长引号整段搬运 Evidence，也不得把原句塞入`若“……”相关事项未核验，可能影响项目判断`等固定外壳。
- 固定章、节标题之外，不允许任何`短标签：正文`式引导语；`宁波政府项目：`、`快速输出：`等任意标签必须改写为完整句子。段落之间只有在存在真实的时间、因果、转折或递进关系时才使用连接词，不连续堆叠`同时`、`此外`、`因此`、`进一步`。
- 正文和表格单元格不得保留 OCR、文件解析或模型输出带入的异常空格。中文字符之间、中文与数字/字母之间、数字与中文单位之间、中文标点前后不留空格；英文单词之间的正常空格保留。
- 禁止`总体来看`、`综上所述`、`值得注意的是`、`需要指出的是`、`不难看出`、`由此可见`、`在此背景下`、`多维度赋能`、`全方位赋能`、`生态闭环`、`新范式`、`实现从……到……的跃升`等明显 AI 套话。
- 事实与分析分离；分析用条件性语言，不把推断写成事实。
- 公司简介优先整合同一证据中的完整法律主体、成立时间、注册资本、完整地址、经营范围或主营业务；不得复述`...展开`、`…展开`、`查看更多`等网页折叠态文本。
- 产品及技术优先采用本地项目文件中的具体产品、平台、系统、模型、算法和技术架构。正文至少写出可识别名称，并说明功能、关键模块、技术路径或成熟度；本地 Evidence 已有具体产品矩阵或技术架构时，不得仅引用公开网页的泛化介绍。
- 公开产品页的站点标题、首页导航、榜单入口、行业目录、登录/关注按钮和页脚不是产品证据。导航与正文被压在同一行时只保留产品正文；无法可靠分离时删除该片段。
- Evidence、文件名、资料库、项目资料、会议纪要、原始文件、检索与核验过程，以及`原文链接`、`来源网址`、页面标题、访问日期和内容指纹，仅保留在任务来源表及审计元数据。相关内容必须先提炼为项目事实、判断或具体待核验事项再进入正文。
- 数字写清时点、期间、币种、单位、是否审计和历史/预测口径。
- 冲突信息并列披露并标记`待核验`。
- 无法形成结论时，正文直接从尚未明确的具体对象和事实写起，再说明对投资判断的影响和下一步核验动作；不得使用`现阶段尚不能形成结论`、`目前无法判断`、`资料不足`、`暂无相关资料`等统一占位前缀，不得描述本地检索、缓存复用、网络补全、资料库或文件读取过程，`资料缺口`仅作为内部状态。
- 全部允许的取证路径仍无可引用证据时，允许保留安全的`资料缺口`并生成受限初稿；不得补造事实、数字或交易结论。
- 亮点综合前文证据；每项风险写清具体风险或触发情形及潜在影响，风险章节整体给出可执行的缓释或核验安排，责任人与时点按实际需要补充；结论直接说明投资逻辑是否成立、成立条件、交易约束、主要风险和关键工作，不显示内部项目阶段。

## 表格槽位

仅在证据结构化且口径一致时创建：股权结构、财务摘要、历史融资、本轮投资方案、经营预测与回报、可比公司估值。不得创建空表。基于已核验输入的机械派生值和明确标注的情景值可以进入表格，但必须来自 Calculation Ledger，并与事实值、管理层预测分列显示。

表格必须先建立 table plan，并按列角色设置 width_weight 和对齐。股权、融资、交易和风险矩阵使用 grid；财务、预测、回报和可比估值优先使用 three-line。列角色不同却等宽、numeric/percent 左对齐或全部表格使用同一样式均为硬错误。
