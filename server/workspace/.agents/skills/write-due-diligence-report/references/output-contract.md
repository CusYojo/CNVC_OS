# 商业尽调报告输出契约

## 输入

必须提供：

- `project`：当前会话绑定且已鉴权的项目字段；
- `sources`：当前项目文件、项目档案、已核验公开材料和用户补充材料形成的有序证据数组；
- `projectKnowledgeBrief`：逐份研读项目资料后形成的主题事实、时间线、冲突、缺口、表格候选和审计信息；
- `sourceCutoffDate`：不晚于运行日的 `YYYY-MM-DD` 日期；
- `parameters.diligenceScope`：`商业尽调`；
- `parameters.userInstructions`：可选的受众、篇幅、关注重点或交易背景。

模板文档只控制结构和版式，不得作为当前项目事实来源。用户补充写作要求可以调整侧重，但不得覆盖项目事实。

## JSON 结构

只返回一个 JSON 对象：

```json
{
  "title": "项目名称尽职调查报告",
  "executiveSummary": "对公司、产品、商业化、财务、交易和风险的事实性综合判断。",
  "sections": [
    {
      "title": "公司基本信息",
      "summary": "本模块的中心判断。",
      "findings": [
        {
          "text": "基于当前项目事实重新组织的自然段。",
          "status": "资料记载",
          "sourceIndexes": [0]
        }
      ],
      "tables": [
        {
          "title": "公司基本信息",
          "unit": "",
          "columns": ["项目", "内容"],
          "rows": [["公司名称", "示例公司"]],
          "status": "资料记载",
          "sourceIndexes": [0]
        }
      ]
    }
  ],
  "highlights": ["有来源支撑且不重复正文的投资亮点"],
  "risks": ["可能影响投资判断或交易安排的风险"],
  "missing": []
}
```

不得增加目录、页眉页脚、来源对象、免责声明、技术日志或 Reviewer 字段。目录和版式由 Formatter 生成。

## 唯一章节顺序

`sections` 必须且只能按以下顺序返回，每项出现一次：

1. 公司情况
2. 交易要点
3. 行业概况
4. 商业模式和经营管理
5. 投资价值与风险
6. 公司基本信息
7. 历史沿革
8. 公司股东情况及实际控制人情况
9. 核心团队介绍
10. 组织架构
11. 关联公司及关联交易
12. 资质、荣誉及法律合规情况
13. 产品概念总览
14. 核心技术路线
15. 产品矩阵
16. 场景应用
17. 核心技术沿革
18. 知识产权及数据权属
19. 商业模式与销售策略
20. 客户验证情况
21. 供应商、采购与成本情况
22. 行业趋势与痛点
23. 市场分析
24. 业务拓展规划
25. 财务情况
26. 投资亮点
27. 公司估值与投资方式
28. 退出方案
29. 风险提示与对策
30. 投资结论及建议

一级部分、编号和目录由 Formatter 根据以上模块映射生成。不得返回旧版“公司与团队、产品与核心技术、后续核验事项”等章节。

## 章组契约

- 30 个模块拆成 11 个章组，每组最多 4 个模块，最多 3 个章组并行。
- 每次请求只返回当前章组的 `sections`；不得一次返回整篇报告。
- 各章组独立解析、校验和保存；失败只重试当前章组。
- 全部章组合并后单独生成 `title`、`executiveSummary`、`highlights` 和 `risks`，再执行全篇 Reviewer。
- 组内标题必须与请求中的标题逐字一致；不得按顿号、逗号或斜线拆分标题。

## 内容和表格

- `summary` 用一至两句概括模块中心判断，不重复 `findings`。
- `findings` 用完整自然段表达具体事实和必要判断，不为满足数量机械拆分。每节可为 0–4 项。
- 两行以上同口径数据优先进入 `tables`。资料充分时，全篇有效表格不少于 12 张。
- 表格只用于真正的行列数据；不得将普通段落包装成表格，也不得为空白、无来源或单项内容凑表。
- 财务表不超过 6 列并保留指标、期间、单位和历史/预测口径；表格全部单元格必须是可显示字符串。
- 同一事实、数字、客户进展、风险或未明确事项只能在最相关模块完整出现一次。

## 状态与引用

内部 `status` 只允许：

- `资料记载`：由输入来源直接支持，`sourceIndexes` 至少一个有效索引；
- `AI推断`：由已识别事实形成的投资分析，仍须保留支持索引；
- `待核验`：已有具体线索但需要原始文件、第三方材料或访谈确认。

`sourceIndexes` 只能是 `sources` 的零基整数索引。状态和索引保存在系统审计记录，不得在客户可见的 `summary`、`finding.text`、表格或结论中显示。正式正文不增加文末引用清单，也不包含免责声明。

最终未明确事项集中写入“风险提示与对策”中的具体风险或工作要求；不得新增独立“资料缺口”或“后续核验事项”章节。`missing` 固定为空数组。

联网环节失败时跳过该来源，继续使用可靠项目事实；不得在任何客户可见字段输出 HTTP 状态、异常堆栈、错误编号或“任务生成失败”。

## 客户可见语言

必须以公司、股东、团队成员、产品、客户、合同、日期、金额或事件作为叙述主体。客户可见字段不得出现：

- 内部项目状态：“线索阶段、进入初筛、申请立项、启动尽调、提请上会、提交投决、继续跟踪、暂缓推进、归档”；
- 生成与取证过程：“项目资料、资料库、根据资料、证据显示、证据不足、联网检索、来源索引、状态标签、Reviewer、LLM、Skill、网关”；
- 模型套话：“值得注意的是、需要强调的是、不难发现、由此可见、综上所述、该信息、该信号、形成闭环、赋能、抓手”；
- 通用流程句：“现阶段建议启动尽调、直接关系到进入下一阶段、将直接影响项目推进、投资团队应据此”。

不得复制证据原文、文件标题、页眉页脚、目录、会议纪要标题、原始编号或过短分片。计划、预测、意向、测试、试用、合同、交付、验收、收入、开票、回款和续约必须严格区分。

## 交付门禁

Formatter 只能消费 Reviewer 通过的 `BusinessContent`。输出 DOCX 必须满足：

- 30 个模块齐全、顺序准确；
- 资料充分时有效表格不少于 12 张；
- 封面、目录、八个一级部分、结尾投资结论、页眉页码和字体层级与主模板接近；
- Word/WPS 打开无修复提示，文字和表格可编辑；
- 正文无状态标签、引用清单、免责声明、技术错误和生成过程。
