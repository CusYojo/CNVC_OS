# 商业尽调报告输出契约

## 输入

必须提供：

- `project`：已获授权的项目字段。
- `sources`：本次运行输入的有序证据数组，按本地项目资料库、当前项目网络缓存、定向网络补全和用户补充输入组织。
- `sourceCutoffDate`：格式为 `YYYY-MM-DD` 且不晚于运行日期的资料截止日。
- `parameters.diligenceScope`：`商业尽调`。
- `parameters.userInstructions`：可选的受众、篇幅、关注重点和交易背景。

不得使用 `sourceCutoffDate` 之后形成的证据。用户补充输入不得替代事实证据。除非用户明确要求只联网搜索，必须先完成本地检索和当前项目网络缓存复用，再对影响判断的具体缺口由 Flue 发现候选 URL、由 LLM Gateway 联网证据服务实际打开并核验页面；不得一开始就进行宽泛的全网搜索。只有主体匹配、正文可读且日期合规的页面才能进入 `sources` 和当前项目缓存；Flue 搜索摘要、搜索结果页、聚合摘要、不可访问页面不得进入 `sources`。不得读取或复制 `docs/` 中特定项目的示例正文；这些内容既不是运行时证据，也不是可复用的报告文本。

## JSON 结构

仅返回一个包含下列键的 JSON 对象：

```json
{
  "title": "项目名称尽调报告",
  "executiveSummary": "一段结合当前项目阶段给出推进、暂缓或归档主建议，并说明最强依据、反向证据、前置条件和下一步动作的摘要。",
  "sections": [
    {
      "title": "投资概要",
      "summary": "本节的一句话结论。",
      "findings": [
        {
          "text": "可复核的尽调发现。",
          "status": "资料记载",
          "sourceIndexes": [0]
        }
      ],
      "tables": [
        {
          "title": "具名、可复核的表格标题",
          "unit": "万元",
          "columns": ["项目", "2025年", "2024年"],
          "rows": [["营业收入", "100", "80"]],
          "status": "资料记载",
          "sourceIndexes": [0]
        }
      ]
    }
  ],
  "highlights": ["有证据支撑的项目亮点"],
  "risks": ["可能影响交易或投资判断的风险"],
  "missing": []
}
```

不得增加附录、来源对象、图表、法律意见或文件版式等字段。`tables`仅用于股权、融资、财务、客户、产品指标和同口径竞品等真实行列数据；不得用表格包装普通段落。版式和目录由渲染器按照核心规范生成，来源明细由系统审计记录保存。

## 必需章节顺序

每个章节必须且只能出现一次，并严格按照以下顺序返回：

1. 投资概要
2. 公司概况
3. 股权结构及融资历程
4. 公司治理与管理团队
5. 法律合规与资质
6. 产品与核心技术
7. 商业模式与经营情况
8. 客户与商业化进展
9. 行业概况与市场空间
10. 产业链与竞争格局
11. 财务分析
12. 估值合理性分析
13. 投资方案
14. 投资亮点
15. 风险分析
16. 后续核验事项

十六个模块的名称、顺序和归章关系必须与核心规范一致。除“后续核验事项”外，每节使用 1–3 项高密度发现；“后续核验事项”最多 8 项。每节摘要均应结论先行。`highlights`和`risks`应分别包含三至八个非空字符串；`missing`固定返回空数组。

## 分章生成与合并契约

正文固定拆为八个独立章组：

1. 投资概要：`投资概要`
2. 公司与团队：`公司概况`、`股权结构及融资历程`、`公司治理与管理团队`、`法律合规与资质`
3. 产品与技术：`产品与核心技术`
4. 业务与商业化：`商业模式与经营情况`、`客户与商业化进展`
5. 行业与竞争：`行业概况与市场空间`、`产业链与竞争格局`
6. 财务与估值：`财务分析`、`估值合理性分析`
7. 投资判断：`投资方案`、`投资亮点`
8. 风险与核验：`风险分析`、`后续核验事项`

单次模型响应只返回一个章组的 `sections`，最多包含四个模块；不得在一次响应中请求或返回全部十六个模块。章组可最多三个并行，但必须独立解析、校验和保存。截断、超时、JSON 不完整或 Reviewer 问题只重试受影响章组，已通过章组不得重新生成。

全部章组通过后，系统严格按“必需章节顺序”合并，再以章节摘要和关键发现为输入单独生成 `title`、`executiveSummary`、`highlights` 和 `risks`。最终 Reviewer 在合并稿上执行；需要修改时必须把问题映射到对应章组定向重写，不得退回整篇一次生成。

执行摘要和“投资概要”必须给出且只给出一个一致、与当前项目阶段匹配的主建议：`进入初筛`、`继续跟踪`、`申请立项`、`启动尽调`、`提请上会`、`提交投决`、`暂缓推进`或`归档`。报告必须围绕当前项目的主体、股权与治理、团队、产品与技术、市场与客户、商业模式、财务、融资与估值、交易方案、风险和可核验来源展开。不得输出脱离具体主体的行业综述、赛道科普或政策堆砌；行业与市场内容只能解释当前项目或具名可比对象。

同一事实、数字、客户进展、风险或后续核验事项只能在最相关章节完整出现一次。执行摘要、投资亮点、风险分析和后续核验不得换词重复正文。不得输出目录、页眉页脚、测试文字、缺口占位语、连续复制内容或整段证据原文。

客户可见内容不得出现“项目资料”“项目材料”“项目资料库”“项目知识库”“资料库”“知识库”“现有资料”“当前资料”“根据资料”“资料显示”“证据显示”“证据不足”“本节”“本初稿”“初步梳理”“结论强度”“检索问题”“联网检索”“来源索引”“状态标签”等取证、检索和生成过程。除“后续核验事项”外，每节应有 1–3 项高密度实质发现；能够合并表达的事实不得拆成多个短条目，不得输出孤立数字、原始编号、会议纪要标题或过短资料分片。

## 客户可见字段改写契约

`executiveSummary`、`summary`、`finding.text`、`highlights`、`risks`以及表格标题、表头和单元格必须由内部事实卡重新组织，不得直接复制输入证据。事实卡只在系统内部使用，至少完成主体、时间、关系、事件阶段、数字口径、披露属性和来源索引的归一化；文件名、片段编号、网页抓取标签和来源处理说明不得进入任何客户可见字段。

正文以具体主体、日期或事件开句，按“事实—影响—边界”推进。仅在披露属性影响结论强度时使用“据公司披露”“管理层预计”“工商登记显示”“监管公告显示”等具体归因。避免“值得注意的是”“需要强调的是”“不难发现”“由此可见”“综上所述”等模型化套话，以及无事实支撑的宣传词；同一模块不得连续机械重复相同连接句式。

模块内容必须与标题语义一致。网页导航、榜单入口、聚合页标签、公司详情页原文不得进入“产品与核心技术”；公司登记信息、客户订单、收费定价、融资估值、法律事项分别进入公司概况、客户与商业化、商业模式、估值及法律合规模块，不得交叉错配。财务表最多六列，必须包含指标或科目以及期间、年度或口径；没有可靠数字时改写为完整的财务限制与投资影响分析。

## 发现状态与引用

仅可使用以下状态：

- `资料记载`：由一项或多项输入来源直接支持的表述；必须至少包含一个有效索引。
- `AI推断`：基于已识别证据形成的合理分析；必须包含支持该分析的索引，并将其表述为分析而非事实。
- `待核验`：已有初步依据，但仍需原始文件、第三方材料、专业人士或访谈确认的表述。

`sourceIndexes` 是输入 `sources` 数组中从零开始的位置。只能使用整数；不得在该字段中输出 `S0` 等标签、来源名称、文件路径或虚构索引。

状态和来源索引仅供系统内部审计。`summary`、`finding.text`、表格标题和单元格不得包含`【资料记载】`、`【AI推断】`、`【待核验】`或其他可见状态标签。

网络缓存和新获取公开材料必须在系统审计记录中分别保留 Flue 候选发现和 LLM Gateway 页面核验状态，并记录当前项目、规范化实体、适用章节、页面标题、规范化 URL、发布主体、发布日期或更新时间、访问时间、有限摘要和内容指纹。新获取结果按 URL 与内容指纹去重写回；与本地资料冲突时并列保留并标记`待核验`。任一联网环节失败时跳过该来源，继续基于本地资料与已有缓存生成，不在客户文档中输出技术报错。

首轮输出中所有`待核验` finding 必须先进入缓存检索和定向联网补全，再以新增证据重新生成受影响内容。最终仍为`待核验`时，只能集中放在“后续核验事项”，最多 8 项；finding 必须包含无法公开核验的具体原因和下一步所需的一手材料，不得只写“资料库未提供”或同类占位语。

## 专题要求

- 研发合作与知识产权：区分任职、联合研发、知识产权权属、许可、转让和作价入股关系；不得仅凭名称、宣传口径或履历关键词认定关系。
- 创始人与团队：写明具名成员、具体职责、任职状态和可核验的研发合作关系，不使用模糊标签代替证据。
- 股权与融资：区分公司陈述、最新工商登记、已签署协议和付款凭证。
- 融资事件：写明具名主体、时间、轮次、金额、投资方和公开披露边界；融资传闻不得写成事实。
- 市场与竞争：只分析与目标项目处置或具名对标直接相关的边界和差异，并区分第三方数据和管理层估算。
- 财务：保留期间、币种、含税口径、合并范围和审计状态，并区分收入、开票和回款。
- 客户与商业化信号：写明主体、产品、时间和阶段，区分线索、测试、试用、已签合同、交付、验收、收入确认、开票、续约和现金回款。
- 产品与技术：区分已展示能力、管理层主张、知识产权权属、外部验证和商业化成熟度。
- 法律合规：仅报告当前项目证据和待核验事项，不得作出法律结论。
- 估值与投资条款：明确假设，并将无证据支持的条款标记为`待核验`。

## 渲染与验收

渲染后的中文 DOCX 必须包含：

- 按顺序排列的全部十六个章节；
- 资料截止日；
- 正文不显示发现状态标签；状态和来源索引仅写入系统审计记录，不在正式正文或文末展示；
- 封面、纵排报告标题、Word/WPS 可更新目录、三分节、正文页码重启、无文字细线页眉、黑体/楷体标题、仿宋正文和表格节奏符合核心规范；
- 文末不包含免责声明、责任声明或引用资料章节；
- 来源索引、项目资料库中已有的网页地址和核验状态保存在系统审计记录中。

凡将无证据支持的主张转化为事实、缺少来源追溯，或暗示尽调已经完成的报告，均应判定为不合格。
