# 合规性说明结构化输出契约

仅返回一个 JSON 对象，顶层字段严格如下：

```json
{
  "title": "关于某项目投资合规性的说明",
  "executiveSummary": "审计元数据，不渲染为正文",
  "sections": [
    {
      "title": "string",
      "summary": "string",
      "findings": [
        {
          "text": "string",
          "status": "资料记载",
          "sourceIndexes": [0]
        }
      ]
    }
  ],
  "highlights": ["审计元数据"],
  "risks": ["审计元数据"],
  "missing": ["审计元数据"]
}
```

## 1. JSON 规则

- 只输出有效 JSON，不使用 Markdown 包裹，不增加字段。
- 使用中文。
- `title` 严格使用 `关于{项目简称}项目投资合规性的说明`。
- `executiveSummary`、`highlights`、`risks` 和 `missing` 只供审计、Reviewer 和界面使用，不得渲染为正文标题或正文附录。
- 每个 finding 对应一个逻辑完整的自然段，可以合并相互依赖的事实、必要判断和成立边界；不得为满足形式把完整意思机械拆开。
- 同一事实、数字、风险或资料缺口只在最相关章节完整出现一次。
- 不输出格式文件名、格式示例正文、测试文字、占位语或连续复制的证据原文。
- 不在 finding 中复述项目资料库、文件名、会议或访谈纪要、项目档案、证据状态或检索过程；先提炼证据，再直接写事实、判断和具体核验条件。
- finding 采用正式说明文件的直接叙述：主体、时间、动作、金额和状态在前，必要判断在后；不使用抽象概念代替项目事实，也不出现“关键核验对象”“关键核验条件”“条件性分析”“条件化判断”“取证边界”“核验边界”等内部审查术语。
- 不使用“具备初步判断依据”“可形成初步投资判断”“已有商业化线索”“具备一定交付组织基础”“成长路径”“支撑强度”“利润留存能力”等模型化套话。
- 相邻 finding 不使用完全相同的开头或收尾模板；“仍需核验”“最终结论取决于”只在确有必要时使用，并明确具体核验对象。

## 2. 八个逻辑章节

`sections` 必须且只能按以下顺序返回：

1. `公司情况介绍`：一级容器，`findings` 为空。
2. `公司简介`：1–2 个事实段。
3. `核心团队`：每名关键人员 1 个 finding，以“姓名（职务）”或明确的姓名—职务句开头；随后写教育、任职经历、项目职责和相关能力。一个 finding 不得混写多名成员，缺人员材料时返回明确缺口。
4. `产品及技术`：一项产品或技术能力 1 个 finding，覆盖名称、核心机制、明确指标或验证阶段、应用价值和边界；知识产权只在“名称—类别—关联技术”关系明确时概括，不为凑段数重复内容。
5. `投资理由`：恰好 5 个 finding，对应五个主题维度；每项按该维度的证据自然组织，不套用固定句序。
6. `投资计划`：覆盖估值、金额、方式、比例、实施主体、交易路径和主要条件。
7. `投资情形分析`：恰好 7 个 finding，按固定合规核查顺序。
8. `结论`：恰好 1 个自然、完整的条件性结论，不要求固定开头；渲染时不显示标题。

逻辑章节不是八个并列版面标题。

## 3. 状态规则

每项 finding 只能使用：

- `资料记载`：由当前项目正式资料直接支持，`sourceIndexes` 至少包含一个有效索引。
- `AI推断`：基于已引用事实形成的审慎判断，必须引用支持证据。
- `待核验`：已有线索但主体、日期、口径、范围、真实性、适用性或效力待确认，必须引用线索来源；网络缓存和新获取的公开补全材料一般使用该状态。
- `资料缺口`：缺少形成最终判断所需材料，`sourceIndexes` 为空；仍须写明本项核查对象、所需材料和完成条件。

正文禁止使用 `当前项目暂无相关资料。` 或其他跨章节重复的统一占位句。存在项目背景证据时，应优先生成有引用的条件化分析；只有没有可引用证据时才使用 `资料缺口`，并在同一 finding 中说明具体核查标准、待取得材料和形成结论的条件。

## 4. 投资理由

投资理由必须恰好五项。每项：

1. 以不超过 30 字、能够被后文事实直接支持的判断句开头；
2. 判断句后使用句号；
3. 再写支持事实、价值关系和必要限制；
4. 不与公司介绍重复整段事实；
5. 直接证据不足时保留该编号：有项目背景证据则说明已有事实及其限制；完全无证据时只说明尚未明确的事实和后续应核对的文件，不凭常识补写项目事实。

五项可从政策与行业、团队、产品技术、客户或生态、商业模式或成长空间中选择最相关主题，但必须由当前项目证据决定。判断句不得写成“已有……线索”“具备……基础”“形成……路径”等空泛概括。

## 5. 投资计划

至少覆盖：

- 投前估值、投后估值和本轮融资总额；
- 我方投资金额；
- 增资、受让或其他投资方式；
- 预计持股比例和计算口径；
- 实施主体及交易路径；
- 主要交易和交割条件。

涉及 SPV、共同投资、资金用途、保护条款或退出安排时，只在有证据时写入。

## 6. 七项合规核查

`投资情形分析` 的七项 finding 内部主题和顺序固定：

1. 投资方式及投资限制；
2. 返投要求；
3. 关联交易；
4. 投资方向；
5. 投资配置；
6. 投资集中度；
7. 其他法律法规、监管规定及基金要求。

每项写成自然衔接的连续段落，不显示编号或“主题：”标签，并写明核查标准、项目及基金事实、计算或比对和单项结论。公开政策、基金公告、返投认定文件、返投公示或公开投资记录可支持 `待核验` 的初步核查；缺少基金内部余额、完整台账、核查表或其他决定性资料时不得作肯定结论，但也不得把已经取得公开依据的整项写成资料全空。

## 7. 数字勾稽

- 投后估值与投前估值、本轮增资金额的口径保持一致；不同口径必须说明。
- 投资金额、估值和持股比例应可相互验证。
- 本基金出资、共同投资总额、SPV 总额和风险敞口不得混写。
- 返投和集中度必须说明基准日、分母和投资口径。
- 关键数字冲突时不自行修正，标记 `待核验`，并登记到 `risks` 和 `missing`。
- `1 0%`、`4 000万`、`3 0人` 等同一数字的抽取空格在单位明确时分别规范为 `10%`、`4000万`、`30人`；不得合并日期或无单位的独立数字。
- 每个 finding 必须以中文句号、问号或感叹号结束。

## 8. 审计来源

来源索引从 0 开始，只能引用实际存在的整数索引。来源披露保留在输出 JSON、产物元数据或审计侧车的末尾，只列正文实际使用来源；不得在核心正文增加“引用资料”板块或可见 `[S#]`。

核心规范只控制结构与风格，不是项目事实来源。网络缓存和新获取的公开补全材料必须保留页面标题、规范化 URL、发布主体、发布日期或更新时间、访问时间、内容指纹、项目大模型名称和统一网关调用标识，并关联当前项目；新获取的有效结果必须来自项目大模型的真实联网能力，写回缓存后才能进入正式 Evidence Packet。普通模型对话、训练记忆和无来源输出不得登记为网络补全材料。

上述来源字段全部属于内部审计信息。Formatter 只读取 finding 的 `text` 作为可见正文，不渲染来源名称，也不允许 `text` 自述“资料显示”“纪要记载”“项目档案显示”或网络检索过程。

该 JSON 只允许进入 DOCX Formatter；最终只生成并登记一份 DOCX，不派生 PDF、Markdown 或其他下载产物。
