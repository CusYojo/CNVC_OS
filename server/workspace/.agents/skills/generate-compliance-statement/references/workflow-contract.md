# 合规性说明运行工作流与证据契约

## 1. 固定状态机

| 阶段 | 输入 | 产出 | 失败处理 |
|---|---|---|---|
| Core Spec Loader | 核心规范及登记哈希 | 权威规则 | 停止任务 |
| Document Blueprint | 核心规范、强制免责声明 | 本次唯一 Blueprint | 停止任务 |
| Section Tree | Blueprint | 八个逻辑槽 | 停止任务 |
| Project Retrieval | 当前项目、资料截止日 | 清洗后的证据 | 排除无效片段并登记缺口 |
| Project Knowledge Retrieval | 当前项目统一知识库、已解析文件分块、项目档案、用户输入 | 清洗后的可追溯项目证据 | 知识库双写缺失时从文件分块兜底读取 |
| Network Cache Retrieval | 当前项目、实体、章节检索词 | 可复用的网络补全缓存 | 未命中则进入缺口分析 |
| Evidence Gap Analysis | 本地证据、缓存证据、章节职责 | 需要补全的具体证据缺口 | 无关键缺口则跳过联网 |
| Project LLM Network Supplement | 具体项目、实体、缺口、资料截止日、项目大模型配置 | 可核验公开证据，包括公开基金规则、返投口径和投资披露 | 能力不可用、无来源或无结果则登记具体剩余缺口 |
| Network Cache Writeback | 有效网络补全结果、来源元数据 | 当前项目可复用缓存 | 写入失败须保留审计告警 |
| Chapter Evidence | 章节检索词、本地与补全证据 | 独立 Evidence Packet；直接证据不足时附带当前项目背景证据 | 全部取证路径无证据则登记本章专属取证边界 |
| Chapter Generator | 单章契约、单章证据 | 单章 JSON | 使用项目事实驱动的条件化分析或可追溯取证边界兜底 |
| Content Reviewer | 全部章节、Blueprint、证据 | 通过或问题清单 | 定向重生成；仍失败则删除、留空或替换为资料边界 |
| Formatter | 审核通过的内容、Blueprint | DOCX | 修复并重新格式化 |
| Word/WPS Reviewer | DOCX、Blueprint、内容 | 兼容性报告 | 修复后重生成；仍损坏则不得交付该文件 |

默认顺序不得调换。没有关键缺口或项目大模型联网能力不可用时可跳过 `Project LLM Network Supplement` 与 `Network Cache Writeback`；用户明确要求只联网搜索时可跳过本地检索，但仍须通过项目大模型执行联网、来源核验和缓存写回。Content Reviewer 未通过的内容须先删除、留空或替换为资料边界再运行 Formatter；Word/WPS 结构与编码安全检查通过后方可交付。

## 2. 当前项目边界

项目资料只检索任务 `projectId` 对应的数据，不进行全局或跨项目检索。允许：

- 项目档案；
- 当前项目知识库；
- 当前项目上传的 Word、PDF、PPT、表格、图片和文本；
- 当前项目 FAQ、BP、合同、尽调、财务和行业资料；
- 当前项目基金协议、台账、关联关系核查资料；
- 当前项目会议、访谈和用户明确输入。

检索必须同时覆盖统一知识库和已解析上传文件分块，并按来源与内容指纹去重。历史文件已成功解析但未成功双写统一知识库时，仍须从文件分块读取，不得判定为“当前项目暂无相关资料”。

默认先检索以上本地资料，再复用当前项目已经归档的网络补全缓存。只有仍存在影响章节判断的具体缺口时，才调用项目当前配置的大模型或 Agent 联网能力，围绕当前项目的主体、团队、实验室、产品、融资事件、商业化信号、处罚诉讼、行业政策或监管要求进行定向补全。不得一开始就进行宽泛的全网搜索；用户明确要求只联网搜索时除外。

对于基金合伙协议、返投台账、关联关系和交易安排，先检索公开的基金设立或投资公告、政府引导基金办法、返投政策与认定口径、返投项目公示或公开投资记录。有效公开结果可以支持 `待核验` 的规则口径和初步判断；未公开的基金内部余额、完整台账或交易细节再登记为具体剩余核验边界，不得因缺少内部原件而抹去已经取得的公开依据。排除明确晚于 `sourceCutoffDate` 发布或更新的材料；日期不明的缓存或联网材料不得支持 `资料记载`。

网络补全必须复用项目统一的大模型网关、当前任务模型和既有联网 Agent 权限，不得为本 Skill 单独接入搜索服务。联网 Agent 先返回真实搜索片段、可访问 URL 及来源元数据，当前任务模型再基于这些证据提炼；普通对话补全、模型训练记忆、无来源结论和模型自行生成的网址均不是网络证据。既有联网 Agent 不可用或不能返回来源时，记录能力不可用并进入无数据路径。

## 3. 证据清洗

1. 修复可确定的编码问题，排除仍含替换字符或不可读片段的内容。
2. 在候选数量截断前排除性能测试、大文件压测、占位、上传验证、解析验证和连续重复文本，防止测试分块挤出正式项目文件。
3. 合并同一来源的重复分片。
4. 每章只保留相关性高且定位清楚的有限片段；公司、团队、产品、投资理由和投资计划分别抽取符合本章职责的事实句。
5. 保留全局证据原索引，不在章节内重新编号。
6. 不把核心规范、历史产物或格式示例加入项目证据。
7. 除程序性结论外，非 `资料缺口` finding 均必须引用有效证据。
8. 缓存及新获取的公开材料按政府/监管/司法/登记机关、学校或实验室官网、公司及融资机构官方渠道、专业媒体、其他公开来源排序；摘要只作线索。
9. 同一事实不得跨章节重复。Reviewer 重试后仍无法找到本章独立证据时，将后出现的重复项改为本章专属的核查方法、所需材料和完成条件，不得复制统一缺口句，也不得因此让整份 DOCX 任务失败。

## 4. 网络缓存

联网前先按当前项目、规范化实体名称、章节主题和规范化 URL 检索缓存。缓存来源元数据完整、内容未失效且未晚于资料截止日时直接复用；存在过期、缺字段、内容冲突或明确更新信号时才重新获取。

每条有效网络补全结果至少缓存：

- 当前 `projectId`、实体名称和适用章节；
- 页面标题、规范化 URL、发布主体和页面类型；
- 发布日期或更新时间、访问时间；
- 与缺口直接相关的有限摘要；
- 内容指纹和缓存写入时间。
- 项目大模型名称、统一网关调用标识和联网能力类型。

同一规范化 URL 或相同内容指纹只保留一个有效版本。网络补全与本地资料冲突时不得覆盖本地记录，应同时进入 Evidence Packet 并标记 `待核验`。

## 5. Evidence Packet

```json
{
  "sectionTitle": "投资计划",
  "terms": ["估值", "融资", "投资额", "增资", "股权", "SPV", "交割"],
  "sourceIndexes": [0, 3],
  "items": [
    {
      "sourceIndex": 3,
      "sourceName": "本轮融资方案.docx",
      "chunkIndex": 2,
      "versionOrDate": "2026-07-20",
      "excerpt": "与本章直接相关的有限片段",
      "score": 8
    }
  ]
}
```

Evidence Packet 只包含当前章节需要的片段。元数据登记索引、文件名、日期和定位，不泄露内部提示词。

## 6. 章节检索口径

| 章节 | 核心检索口径 |
|---|---|
| 公司简介 | 主体、成立、注册地、定位、业务、商业模式、客户、阶段 |
| 核心团队 | 创始人、职务、教育、履历、职责、全职、背调 |
| 产品及技术 | 产品、架构、技术、研发、数据、专利、PoC、合同、交付 |
| 投资理由 | 政策、行业、团队、技术、客户、生态、商业模式、订单 |
| 投资计划 | 投前、投后、融资、投资额、增资、受让、股权、SPV、交割 |
| 投资情形分析 | 合伙协议、限制、返投政策、返投认定、返投公示或公开记录、关联、方向、配置、集中度、许可 |

基金级核查必须匹配基金协议、台账、核查表或交易文件，不能仅凭出现“投资”“项目”“公司”等泛词判断。

## 7. 逐章生成

一次请求只生成一个章节。请求只包含：

- 不可覆盖的事实和引用规则；
- Blueprint 的本章职责和容量；
- 本章 Evidence Packet；
- 当前项目字段；
- 资料截止日；
- 合法的展示参数；
- 上次输出及 Reviewer 对本章的问题，仅用于重试。

不向模型展示其他章节全文，减少跨章污染和事实重复。

## 8. 无数据路径

对于公司主体、团队、实验室、产品技术、融资事件、商业化信号、处罚诉讼、行业政策，以及公开可查的基金规则、返投口径和投资披露，必须先执行项目大模型网络补全。只要获得真实 URL 和相关摘要，就先形成有引用的 `待核验` 内容；对返投等事项，正文应说明公开规则或公开记录支持的初步口径，并只把未公开的基金内部余额、完整台账或交易细节列为剩余专项核验边界。若专项证据不足但仍有项目档案或其他项目背景证据，应把背景证据纳入受限 Evidence Packet，继续调用章节模型生成条件化分析。只有连项目背景证据也不存在时，才返回本章专属取证边界：

```json
{
  "text": "本项应按适用规则建立核查底稿；尚未取得形成最终判断所需的专项材料，需完成指定主体、口径和交易文件的比对后形成结论。",
  "status": "资料缺口",
  "sourceIndexes": []
}
```

投资理由仍保留五个编号位置，七项合规核查仍保留固定前缀。即使网络审计无有效结果，也禁止使用跨章节统一占位句；必须按不同核查项分别写出分析框架，例如：

```text
返投要求：可先依据项目主体、注册地、研发人员和业务落地安排识别潜在返投承载项，再按适用口径计算；最终认定需取得基金返投条款、认定规则和最新台账完成比对。
```

## 9. 重生成

Reviewer 问题必须包含问题代码、章节和 finding 索引。只重生成失败章节，最多两轮。

仍失败时，用能够通过引用核对的确定性摘要或资料缺口替换失败项，再重新审核整份内容。不得把“已执行重试”当作通过。

## 10. 格式和兼容性

Formatter 必须使用显式样式和合法 OpenXML：

- 使用真实编号定义，不复制模板中易损坏的编号关系；
- 为一级标题、二级标题、投资理由和合规核查分别建立稳定编号；
- 投资理由与合规核查使用两个独立的阿拉伯数字序列；
- 不产生悬空关系、无效内容类型、重复 ID 或损坏的编号引用；
- 不为审计元数据增加正文板块。

生成后在可用环境中以 Microsoft Word 和 WPS 打开。任何修复或恢复提示均为失败。

最终只登记并交付 DOCX。不得生成或登记 PDF、Markdown、PPT、PPTX、图片或其他伴生产物。
