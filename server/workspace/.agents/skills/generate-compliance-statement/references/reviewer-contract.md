# 合规性说明 Reviewer、Formatter 与兼容验收

## 1. Content Reviewer

以下检查用于在进入 Formatter 前清除不安全内容。联网、模型或内容 Reviewer 异常不得直接终止任务；未通过项必须删除、留空或替换为可追溯的资料边界后再进入 Formatter。

### 1.1 结构

- 标题严格为 `关于{项目简称}项目投资合规性的说明`。
- 八个逻辑槽名称、数量和顺序正确。
- `公司情况介绍` 只作容器，findings 为空。
- 公司简介、核心团队、产品及技术完整。
- 投资理由恰好五项。
- 投资情形分析恰好七项且顺序固定。
- 结论恰好一项，以“综上”开头且不显示为版面标题。

### 1.2 证据与幻觉

- 除程序性结论外，`资料记载`、`AI推断` 和 `待核验` 至少引用一条有效证据。
- 引用与 finding 的主体、数字、专名和判断直接对应。
- `资料缺口` 不带来源，并明确本项核查对象、待取得的具体材料和形成结论的完成条件。
- 正文不得出现 `当前项目暂无相关资料。` 或跨章节连续复制的统一缺口占位语。
- 不出现非当前项目的主体、人员、数字、日期或交易条款。
- 不虚构法规、许可、审批、基金条款、返投、关联关系、集中度、估值、金额或比例。
- 不把预测、意向、访谈或主体自述写成已交付、已签约或已回款事实。
- 除非用户明确要求只联网搜索，审计记录必须证明已按“本地项目资料库 → 网络缓存 → 项目大模型定向网络补全”的顺序取证，不得一开始就进行宽泛的全网搜索。
- 网络补全必须使用项目统一大模型网关、当前任务模型或既有 Agent 联网能力；不得由本 Skill 单独调用搜索引擎、第三方搜索 API 或抓取服务。
- 网络缓存和新获取的公开补全来源必须保留页面标题、规范化 URL、发布主体、发布日期或更新时间、访问时间、内容指纹、项目大模型名称和统一网关调用标识；新获取的有效结果必须已写回当前项目缓存。
- 普通模型对话、训练记忆、无 URL 结论或模型自行生成的网址不得作为联网结果；模型没有真实联网与来源引用能力时必须报告能力不可用。
- 只引用网络缓存或新获取公开材料的 finding 必须标记为 `待核验`。
- 网络补全与本地原始记录冲突时必须并列披露并标记 `待核验`，不得覆盖本地证据。
- 对公开可查事项，在没有项目大模型网络补全审计记录时不得输出资料全空结论。
- 公开监管规则、基金公告、返投认定文件、返投公示或公开投资记录必须用于形成 `待核验` 的初步核查；不得据此声称本基金内部余额、完整台账或本次交易已经满足限制。
- 已取得相关公开依据的核查项不得整体退回资料全空结论；只能在同一 finding 中说明尚未公开的具体内部数字或交易细节。

### 1.3 一致性与数字

- 同一事实、数字、风险或缺口不跨章节重复完整表述。
- 投前估值、投后估值、融资额、投资额和持股比例口径一致。
- 基金出资、共同投资、SPV 总额和风险敞口不混写。
- 返投和集中度写明基准日、分母、计算过程和比较结果。
- 数字冲突时不自行修正。
- 存在待核验或资料缺口时不使用无保留合规结论。

### 1.4 正文边界

- 不增加封面、执行摘要、责任声明、风险提示、资料缺口或引用资料正文板块。
- 不显示状态标签、`[S#]`、模板路径、Skill 名称或生成引擎。
- 审计元数据不混入正文。

## 2. 问题代码

至少支持：

- `TITLE_MISMATCH`
- `SECTION_MISSING`
- `SECTION_ORDER`
- `SECTION_COUNT`
- `CONTAINER_CONTENT`
- `REASON_COUNT`
- `CHECKLIST_ORDER`
- `CONCLUSION_INVALID`
- `SOURCE_INDEX_INVALID`
- `CITATION_MISSING`
- `CITATION_IRRELEVANT`
- `MISSING_DATA_WORDING`
- `TEMPLATE_FACT_LEAK`
- `TEMPLATE_COPY`
- `DUPLICATED_FACT`
- `NUMERIC_RECONCILIATION`
- `UNQUALIFIED_CONCLUSION`
- `BODY_APPENDIX_DRIFT`
- `RETRIEVAL_ORDER`
- `NETWORK_SOURCE_METADATA`
- `NETWORK_CACHE_WRITEBACK`
- `PROJECT_LLM_GROUNDING_UNAVAILABLE`
- `UNVERIFIABLE_MODEL_SOURCE`

问题必须包含代码、章节、finding 索引和可执行修复要求。

## 3. Formatter

Formatter 只消费审核通过的 JSON 和 Blueprint，不重新创作业务内容。

### 3.1 Word 版式

- A4 纵向，单节，左右 1800 DXA、上下 1440 DXA。
- 无可见页眉、页脚、页码、目录、表格、图片或浮动对象。
- 标题为黑体 14 pt、常规、居中、1.5 倍行距。
- 一级标题为宋体 12 pt、加粗、段前 12 pt。
- 二级标题为宋体 12 pt、加粗；正文为宋体 12 pt；均为 1.5 倍行距。
- 一级标题必须显式清除字符首行缩进；二级标题必须显式设置左缩进 0 DXA、首行缩进 482 DXA，禁止由 `List Paragraph` 默认样式叠加缩进。
- 正文两端对齐，首行缩进约 482 DXA。
- 理由和核查条目无首行缩进，判断句或冒号前加粗。
- 落款和日期右对齐。

### 3.2 编号

- 一级标题显示 `一、` 至 `四、`。
- 二级标题显示 `（1）` 至 `（3）`。
- 投资理由显示 `1、` 至 `5、`。
- 投资情形分析重新从 `1、` 开始并显示至 `7、`。
- 使用合法、独立的 Word 编号定义，不把标号写成 Markdown 星号或 Unicode 圆点。

### 3.3 分页

- 标题与首章不形成异常大空隙。
- 一级、二级标题不孤立在页尾。
- 落款和日期不拆页。
- 不出现仅剩少量文字的异常空白尾页。
- 不通过缩小字号或压缩行距控制页数。

## 4. Word Reviewer

检查：

- DOCX 为有效 OpenXML ZIP，所有 XML 可解析。
- `[Content_Types].xml`、关系、样式、字体和编号引用闭包完整。
- 不存在悬空关系、重复 ID、无效编号引用或 U+FFFD。
- 标题、四章、三个子节、五项理由、七项核查、结论和落款完整。
- 页面、边距、字体、字号、行距、缩进和编号符合 Blueprint。
- 无多余正文板块和非本项目事实泄漏。

失败时修复 Formatter 并重新生成一次；仍无法生成可由 Word/WPS 正常打开且无乱码的 DOCX 时，才按基础设施异常停止，不得交付损坏文件。

## 5. Microsoft Word / WPS 兼容验收

在应用可用时分别打开最终 DOCX，检查：

1. 不出现“发现无法读取的内容”、修复、恢复或另存为新文档提示。
2. 中文无乱码、方框字或字体替换。
3. Word/WPS 字体栏能识别标题黑体 14 pt、正文宋体 12 pt。
4. 一级、二级标题均为宋体 12 pt 加粗，编号未因 `List Paragraph` 字符首行缩进整体右移；四级编号显示正确，两个阿拉伯数字序列分别从 1 开始。
5. 页面没有文字重叠、裁切、孤立标题或异常空白尾页。
6. 落款与日期完整且右对齐。

出现任一问题即返回：

- `WORD_REPAIR_REQUIRED`
- `WPS_REPAIR_REQUIRED`
- `FONT_MISMATCH`
- `NUMBERING_INVALID`
- `EMPTY_TAIL_PAGE`
- `LAYOUT_OVERFLOW`

不得交付需要恢复才能打开的文件。

## 6. 单一交付物

只允许登记并交付一份通过 Word/WPS 结构与编码安全检查的可编辑 DOCX。内容 Reviewer 的剩余问题必须先通过删除、留空或资料边界替换消除；出现 PDF、Markdown、PPT、PPTX、图片或其他伴生产物时，删除伴生产物并保留 DOCX，不把整项任务标记为失败。
