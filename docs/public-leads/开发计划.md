## 2. 当前端到端架构

```text
36氪 lead_reserve ── daily_intake.mjs ───────────────┐
                                                     │
GSData / RSS / arXiv / 微信聊天                       │
  → project-discovery FastAPI                        │
  → data/*.jsonl                                     │
  → GET /api/candidates                              │
  → Node POST /api/leads/sync-radar ────────────────┤
                                                     ▼
                                              PostgreSQL leads
                                                     │
                 Project data + Flue score ◄────────┤
                                                     │
React /sourcing ◄─ Store ◄─ Node GET /api/leads ─────┘
```

外部依赖：

- PostgreSQL 16：主线索、项目、审计数据。
- Radar FastAPI：GSData、RSS、arXiv、微信聊天等候选采集。
- Flue：`score-project`、`score-paper`；评分阶段只读取已入库资料。
- 项目资料库：AI 评分只使用已入库且可追溯的资料；外部数据须经过独立批准后先入库。
- cron/systemd：当前生产说明中的每日摄入、批量补漏与进程守护。

部署现状限制：

- `docker-compose.yml` 仅编排 PostgreSQL，Node、Radar、Flue 依赖外部进程。
- Radar 和 Node 的任务状态均为进程内状态，服务重启后不具备可靠恢复能力。
- 配置文档存在 Flue/Radar 端口差异；进入发布实施前必须形成环境矩阵。

## 5. 开发顺序分类

SYS-001 的 P0 约束适用于线索抓取和数据质量工作。它提高 POOL-001/002/009（新）/013/014 的资源优先级，但不允许跳过来源、阈值、审核、迁移和发布确认。

### 可直接编码并独立验收

- LEAD-TASK-001：建立测试与合同骨架；属于工程前置，不直接关闭业务需求。
- LEAD-TASK-028：`addLead`/`convertLead` 及共享类型基线修正已存在，当前 `npm run check` 通过；可立即补公共池 Promise、loading、错误提示和竞态测试并完成基线验收。
- LEAD-TASK-029：修复情报采集重复创建。
- LEAD-TASK-030：修复无证据时项目名冒充公司主体。
- LEAD-TASK-031：修复当前融资读取路径和投资方过滤不一致。

### 可立即排查或技术预研

- LEAD-TASK-003～005、007～008：可先完成现状测量、接口草案、执行计划和技术选型；排序窗口、历史保留、队列、告警和性能阈值未确认前，不宣称完整任务可验收。

### 确认后立即执行

- LEAD-TASK-002、006：依赖 SLA、自动调度和通知策略。
- LEAD-TASK-009～012：依赖主体唯一键、冲突优先级和历史范围；LEAD-TASK-010 在稳定键确认前保持阻塞。
- LEAD-TASK-019：依赖渠道取消范围。
- LEAD-TASK-023～026：依赖名称规则、主体证据、转换能力去留和融资多轮规则。
- LEAD-TASK-032～036：依赖估值来源白名单、规范合同、自动展示阈值、审核角色、频率、成本和历史范围；032 可先做来源盘点与合同草案，但批准前不接生产检索。

### 必须等待产品/设计定义

- LEAD-TASK-013～018：当前静态行业/地区和只读标签可做回归，但正式标签式首页、业务维度和项目标签等待定义。
- LEAD-TASK-020～022：当前临时估值和六列布局可做回归，但规范估值口径和整体列表原型等待确认。
- LEAD-TASK-027、035：当前核心列可做回归，但技术评分、新鲜度、候选审核和首页正式原型等待确认。

### 可并行关系

- 运行可观测（005）可与列表性能（008）并行。
- 持久评分队列（007）可与来源身份模型（009）并行。
- 标签字典（015）确认后，标签式入口（013）和标签存储（017）可并行。
- 主体证据模型（024）与融资 DTO（026）可并行；两个确定性缺陷任务 030、031 也可彼此独立，但共享 Radar/Node 合同测试。
- 自动估值合同（032）批准后，检索抽取（033）和候选存储设计（034）可并行；审核 UI（035）依赖 034，回填调度（036）依赖 033/034。

### 高风险任务

- LEAD-TASK-004：原始 JSONL Upsert，错误写入可能破坏源数据。
- LEAD-TASK-007、009～012：评分任务、稳定身份、事务合并、字段历史和历史回填，存在重复、误合并与不可逆数据影响。
- LEAD-TASK-015～018：维度和标签模型会影响页面、统计、项目标签和历史数据。
- LEAD-TASK-020～021：估值口径、规范化与回填涉及多轮、多币种和来源冲突。
- LEAD-TASK-024～026：主体证据、转换能力退场和融资 DTO 涉及数据正确性、历史数据与接口兼容。
- LEAD-TASK-027：跨需求集成、迁移、性能和发布门禁。
- LEAD-TASK-032～036：联网估值涉及虚假数据、来源条款、人工审核、外部成本、批量回填和投资判断风险。

### 推荐首任务与模块内顺序

- **推荐第一个开发任务**：LEAD-TASK-029，并同步补充 LEAD-TASK-001 的最小回归 fixture。重复创建路径明确、范围小、无数据库迁移，可形成最短可提交和可验收闭环。
- **推荐顺序**：LEAD-TASK-001（最小骨架）→ LEAD-TASK-029 → LEAD-TASK-028（补测试并验收现有签名修正）→ LEAD-TASK-030～031 → 当前 013～014/016～017/019/021～022/027/035 已实现片段的回归与差异取证 → LEAD-TASK-003～005、007～008 的排查/设计 → LEAD-TASK-002、006（SLA/调度确认后）→ LEAD-TASK-009～012（稳定键和冲突规则确认后）→ LEAD-TASK-015～018、020～021（字典/估值确认后）→ LEAD-TASK-032（来源与规范确认）→ LEAD-TASK-033～034 → LEAD-TASK-036 → LEAD-TASK-013～014、019、022～027、035 的剩余正式能力（设计、审核与字段口径确认后）。

- POOL-011～014 属于 V1.2 新增需求；任务进入开发前还需关闭 `待确认事项.md` 中对应 V1.2 问题，不能只沿用 V1.1 的 Q-POOL 编号。

## 6. 完成定义

每项项目需求关闭前至少满足：

1. 正式项目需求与待确认问题已有决议记录。
2. API、数据模型和迁移有版本及向后兼容说明。
3. 类型检查、单元、集成、合同和关键 E2E 通过。
4. 真实数据样本完成数据质量验收。
5. 日志不包含密钥、令牌或不必要的正文隐私数据。
6. 监控、告警、运行手册和回滚步骤已验证。
7. 历史回填可 dry-run、可审计、可暂停、可回滚。
8. 需求追踪中记录发布版本、验收人、证据链接和遗留项。
