# 公共线索池测试计划

> 正式依据：`docs/需求分析.md` V1.2。  
> 本文覆盖 POOL-001～POOL-014，并分别验证 POOL-009 旧口径和新口径。  
> 任务覆盖：LEAD-TASK-001～LEAD-TASK-036。  
> 本文是辅助测试建议，不替代正式项目需求、产品验收标准或上线审批。
> SYS-001 将线索池抓取和数据质量列为 P0；测试资源优先保障对应链路，但未确认阈值仍以待确认状态执行。

## 1. 测试目标

1. 验证 Radar 采集、主平台同步、AI 分析、数据库和 `/sourcing` 展示形成可恢复的数据闭环。
2. 验证增量更新不漏数、不静默覆盖人工值、不在并发下制造重复。
3. 验证业务标签、估值、主体和融资字段具有一致口径、来源证据、更新时间和人工优先规则。
4. 验证首页核心展示、筛选、分页、统计和详情在真实数据量下准确、稳定、可访问。
5. 验证自动估值只使用批准来源，不把融资金额当估值，不在无证据时生成具体数值，并能审核、过期和回滚。
6. 验证迁移、历史回填、灰度和回滚可以安全执行。

## 3. 测试环境

### 3.1 本地/CI

- PostgreSQL 16 独立测试库，不复用开发或生产数据卷。
- Node Express 使用测试环境变量和随机数据库。
- Radar 使用临时数据目录，不写 `project-discovery/data/` 正式文件。
- GSData、RSS、arXiv、Flue、SearXNG 和自动估值来源使用录制 fixture 或 mock server；自动估值 fixture 只能来自批准或合成内容。
- 前端使用独立测试账号和固定时区 `Asia/Shanghai`。

### 3.2 集成环境

- Node、Radar、Flue、SearXNG、PostgreSQL 均按生产近似拓扑部署。
- 使用脱敏数据快照，至少覆盖：
  - 36氪来源。
  - 机构公众号。
  - 高校公众号。
  - 创投新闻。
  - 微信群聊。
  - arXiv。
  - 人工/BP。
- 开启结构化日志、同步 runId 和性能指标。

### 3.3 灰度环境

- 使用生产同版本数据库 schema。
- 仅启用 1～2 个来源 canary。
- 禁止在未审批的情况下执行全量历史回填。

## 4. 测试数据策略

### 4.1 黄金样本集

建立版本化、脱敏的 fixture：

- 明确法定主体全称及来源证据。
- 只有品牌/产品名，无公司主体。
- 实验室、高校课题组、论文等非公司主体。
- 同名不同公司。
- 公司曾更名或项目更名。
- 多轮融资、多币种、投前/投后估值。
- 来源公众号名称与投资机构相同或混合出现。
- 人工已确认字段与 Radar/AI 冲突。
- 只有融资金额但没有估值。
- 缺失估值且存在单一可信来源。
- 缺失估值且多个来源冲突、页面过期或无公开信息。
- 搜索结果含同名公司、恶意提示、付费墙、转载和来源失效。
- 空值、占位值、错误格式和超长文本。
- 噪音文章、政策、论坛、招生、党建等非项目内容。

黄金样本不得包含真实密钥、个人联系方式或不必要的原始隐私正文。

### 4.2 容量建议数据集

以下数量是待评审的技术建议，不替代 ACCEPT-002、POOL-013/014 的正式容量和并发输入：

- 10,000 条：开发性能基线建议。
- 100,000 条：索引、分页、统计和搜索压力建议。
- 1,000 条单批候选：cursor 和分批同步建议。
- 100 条并发相同身份请求：幂等与锁验证建议。
- 自动估值批量规模、单来源 QPS、日预算和并发数：待来源条款、成本和运维确认。

### 4.3 历史回填数据

- 使用生产脱敏快照。
- dry-run 输出新增、更新、冲突、跳过和低置信度清单。
- 以固定 checksum 对比迁移前后行数和关键字段。

## 6. 非功能测试

### 6.1 性能

指标待 LEAD-TASK-002 确认，至少记录：

- Radar 单来源抓取耗时和吞吐。
- 主平台每 100 条同步耗时。
- 列表/详情/统计/facets p50、p95、p99。
- 评分排队时间、执行时间和积压。
- PostgreSQL CPU、连接数、锁等待和慢查询。
- JSONL 文件大小增长下的读取和 Upsert 时间。
- 自动估值检索排队、单候选成本、来源限流、候选产出率、审核积压和日预算。

### 6.2 稳定性与恢复

- Radar、Node、Flue、SearXNG、PostgreSQL 分别不可用。
- 网络超时、连接重置、部分响应和畸形 JSON。
- 任务执行中进程退出。
- cursor 提交前后崩溃。
- 数据库事务死锁和连接池耗尽。
- cron 重叠与多实例并发。

### 6.3 安全

- Node JWT 和内部密钥鉴权。
- Radar 写接口不得匿名暴露到非可信网络。
- 内部密钥不可使用仓库默认值进入生产。
- 日志和任务表不得存令牌、密钥、个人联系方式或不必要全文。
- 标签编辑、人工确认、重试和历史恢复执行角色校验。
- SQL/JSON/搜索输入边界与注入测试。
- 自动估值检索必须防 SSRF、开放重定向、搜索/Prompt 注入和非白名单来源绕过。
- 来源证据、审核接口和历史候选执行线索/角色权限；日志不保存无必要网页全文。
- 验证来源条款、版权和公司数据合规要求对应的技术限制已生效。

### 6.4 可访问性与兼容

- Chrome 当前支持版本；如产品要求，再扩 Safari/Edge。
- 目标桌面分辨率及确认的最小宽度。
- 键盘焦点、标签语义、按钮名称、色彩对比。
- 中文长名称、英文公司名、特殊字符和超长融资文本。

## 7. 数据质量验收

需要产品/数据共同确认阈值：

| 指标 | 定义 | 当前不可直接设定的原因 |
|---|---|---|
| 主体识别准确率 | 自动识别主体中正确记录占比 | 需真实黄金样本和“正确主体”定义。 |
| 主体识别覆盖率 | 应有主体样本中被识别占比 | 论文/实验室等不一定应有公司主体。 |
| 融资字段准确率 | 轮次、金额、估值、机构逐字段准确率 | 需多来源冲突和多轮规则。 |
| 重复率 | 同一稳定主体重复 lead 数 | 稳定主体键待确认。 |
| 漏同步率 | 来源新增/更新但未进入主库的比例 | 需 source identity 和游标。 |
| 噪音误入率 | 非项目内容进入公共池比例 | 需产品标注样本。 |
| 时效达标率 | 各阶段在 SLA 内完成比例 | SLA 待确认。 |
| 业务标签准确率 | 行业、地区等自动标签逐维度准确率 | 正式字典、来源和人工确认规则待定。 |
| 自动估值候选准确率 | 候选金额、币种、口径、日期和主体均正确的比例 | 需来源白名单、黄金样本和阈值。 |
| 自动估值来源覆盖率 | 缺估值样本中找到可靠公开证据的比例 | 无公开信息不是系统错误，需分母定义。 |
| 错误自动展示率 | 未经批准或低于阈值的候选被当作正式估值展示的比例 | 自动展示规则和审核边界待确认。 |
| 估值审核时效 | 候选创建到批准/驳回的时间 | 审核角色和 SLA 待确认。 |

所有质量报告必须同时给出样本量、来源分布、抽样方法和置信区间或误差说明，不能只给单一百分比。

## 8. 迁移与回填测试

1. 生产脱敏快照执行 schema migration。
2. 验证 migration 可重复执行或具备明确版本锁。
3. dry-run 不写业务表，只输出变更计划。
4. 抽样复核高、中、低置信度记录。
5. 分批 apply，记录 checkpoint、runId 和每批 checksum。
6. 执行 verify：
   - 行数对账。
   - 唯一键冲突。
   - 关键字段 before/after。
   - 低置信度未被自动覆盖。
7. 在同一快照执行 rollback，验证恢复。
8. 完成性能和锁影响评估后才能进入生产。
9. 自动估值候选、证据和审核表从空库及当前 schema 升级；旧估值不得自动标记为已审核。
10. POOL-014 历史回填按 runId/checkpoint 恢复和撤销，不覆盖人工值或原始证据。

## 10. 准入与退出标准

### 开发提测准入

- 本次提测任务直接关联且会改变实现方向的待确认问题已决议；无关需求不得阻塞独立发布单元。
- 类型检查和单元测试通过。

### 测试退出

- P0/P1 缺陷为 0。
- P2 缺陷有产品/技术负责人书面接受及后续任务。
- 核心 E2E、数据质量、迁移、性能、恢复和安全测试通过。
- 所有失败场景有用户可理解状态或运维可观察记录。
- 发布计划中的监控与回滚演练完成。
