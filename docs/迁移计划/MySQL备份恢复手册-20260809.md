# MySQL 备份、库存与恢复演练手册

## 1. 适用范围和当前结论

本手册用于单服务迁移目标库的迁移前逻辑备份、备份库存核验和隔离恢复。应用连接继续读取 `.env` 中的 `DB_HOST`、`DB_PORT`、`DB_DATABASE`、`DB_USERNAME`、`DB_PASSWORD`、`DB_FREFIX`；命令、报告和文档不得打印连接身份或凭据值。

当前技术目标为：一致性快照 RPO 0 行、备份不超过 300 秒、恢复不超过 300 秒。恢复时限现在由代码强制执行，超限即失败并精确清理本次隔离前缀，不再只是报告字段。

## 2. 权限和破坏面边界

- 备份使用 Runtime 账号，只读取 `DB_FREFIX` 指定的活动表，不执行源库 DDL/DML。
- 恢复使用 root-owned `.runtime/secrets/mysql-migration.env` 中的 Migration 账号；该账号只拥有当前数据库内的目标 Schema DML 与 `CREATE/ALTER/DROP/INDEX/REFERENCES`，不需要 `CREATE/DROP DATABASE`。
- 恢复在同一数据库的随机隔离前缀 `rb_accept_<随机值>_` 或经批准的 `rollback_<标识>_` 下执行，禁止覆盖当前活动前缀。
- 验收脚本只删除本次生成且通过严格正则校验的隔离前缀表，不修改 `.env`，不自动切流。
- 备份目录与证据目录必须为普通目录、不得是符号链接，权限 `0700`；备份与报告必须为普通文件、不得是符号链接，权限 `0600`。

## 3. 正式备份和库存核验

迁移或 Schema 变更前执行：

```bash
npm run db:backup
npm run accept:mysql-backup-inventory
```

默认备份写入 `.runtime/mysql-backups/mysql-pre-migration-<时间>.jsonl.gz`，相邻 `.report.json` 保存格式版本、表数、行数、SHA-256、耗时和权限结论。命令拒绝覆盖已有文件。

生产应使用批准的绝对路径：

```bash
npm run db:backup -- --output /approved/owner-only/mysql-pre-migration-<change-id>.jsonl.gz
```

库存验收会完整读取 gzip 逻辑格式，核对 Header/Footer、备份 SHA、表数、行数、前缀、相邻报告、目录/文件权限、最新备份时效，并要求最近一次成功恢复演练覆盖最新备份的表数和行数。输出只保存备份内容哈希和汇总，不保存数据库连接身份、路径或业务正文。

## 4. 隔离恢复演练

```bash
npm run accept:mysql-backup-restore
```

命令执行：

1. 使用与 Schema 迁移相同的 MySQL advisory lock，阻止快照期间发生迁移 DDL。
2. 在 `REPEATABLE READ` 一致性快照中读取当前前缀的全部基础表 DDL 和数据。
3. 拒绝当前前缀范围内未被格式支持的 View、Trigger、Routine 和 Event，避免静默漏备。
4. 创建临时 owner-only gzip JSONL 备份并计算 SHA-256。
5. 使用 Migration 账号把备份恢复到同一数据库的随机隔离前缀。
6. 比较全部表的规范化 DDL、行数和排序无关的逐行内容 SHA-256。
7. 强制检查 300 秒恢复时限；超时或任何内容不一致均失败关闭。
8. 精确删除隔离前缀，确认当前活动前缀表数不变，并删除临时备份。

任何步骤失败都会返回非零退出码；失败清理也只能作用于本次严格校验过的隔离前缀。

## 5. 人工回退准备

先预检，不写数据库：

```bash
npm run db:rollback:preview -- \
  --backup /approved/owner-only/mysql-pre-migration-<change-id>.jsonl.gz \
  --target-prefix rollback_<8至16位小写字母或数字>_
```

经维护窗口批准后才允许应用：

```bash
npm run db:rollback -- \
  --backup /approved/owner-only/mysql-pre-migration-<change-id>.jsonl.gz \
  --target-prefix rollback_<8至16位小写字母或数字>_
```

应用仍不修改当前 `DB_FREFIX`。恢复及内容校验通过后，须由发布指挥确认写入冻结、Point of No Return 和新旧数据差异，再人工修改 `DB_FREFIX` 并仅重启 `cybernaut-app.service`。切流后已经产生 MySQL 新写入且没有反向 CDC 时，不允许直接回切，应执行批准的前向修复。

## 6. 保存、保留和责任策略

| 项目 | 技术基线 | 生产要求 |
|---|---|---|
| 本地保存位置 | `.runtime/mysql-backups/` | `MYSQL_BACKUP_ROOT` 指向受控绝对路径 |
| 最低保留期 | 35 天 | `MYSQL_BACKUP_RETENTION_DAYS`，不得低于 7 天；业务/合规可提高 |
| 新鲜度 | 本机默认 168 小时 | 生产默认 26 小时 |
| 恢复演练新鲜度 | 30 天 | `MYSQL_RESTORE_DRILL_MAX_AGE_DAYS` |
| 本地访问权限 | 目录 `0700`、文件 `0600` | 独立备份主体与最小权限 ACL，不得由 Web 用户访问 |
| 异地副本 | 本机可暂缺但报告明确为未满足生产要求 | 必须设置不含密钥的 `MYSQL_BACKUP_OFFSITE_LOCATION_ID` |
| 介质加密 | 本机报告真实状态 | 生产必须 `MYSQL_BACKUP_ENCRYPTION_AT_REST_CONFIRMED=true` |
| 备份执行责任 | `database-operations-on-call` | `MYSQL_BACKUP_OWNER_ROLE` 可替换为正式值 |
| 恢复指挥责任 | `migration-release-commander` | `MYSQL_RESTORE_OWNER_ROLE` 可替换为正式值 |
| 数据批准责任 | `data-owner` | `MYSQL_BACKUP_APPROVER_ROLE` 可替换为正式值 |

自动备份、异地复制和生命周期删除应由 MySQL/基础设施备份平台承担，不新增本项目业务 service、cron 或 systemd timer。这样生产仍只保留一个项目业务单元 `cybernaut-app.service`。应用仓库只负责变更前备份、库存失败门禁、恢复工具和证据格式。

## 7. 当前实测证据

2026-08-11 对当前 MySQL 目标完成两类演练：

- 正式迁移前备份：73 张表、67,708 行，备份与报告均为 `0600`。
- 最新临时一致性备份及恢复：74 张表、67,771 行，RPO 0 行；0035 前的正式迁移前备份仍为 73 张表、67,708 行，生产最终停写点必须重新生成正式备份。
- DDL、行数和内容 SHA-256 全部一致。
- 恢复使用随机隔离前缀，隔离表已精确删除，活动前缀保持不变。
- 临时备份已删除，连接身份和密钥均未写入证据。

库存报告位于 `.runtime/migration-evidence/mysql-backup-inventory/report.json`，恢复演练报告位于 `.runtime/migration-evidence/mysql-restore/<run-id>/report.json`，均不纳入版本控制。

## 8. 尚未由本机证据关闭的事项

本机演练不能替代以下生产现场工作：

1. 设置受控绝对备份根、异地加密介质和对象生命周期策略。
2. 把三个责任角色替换为生产值并取得数据、运维和安全批准。
3. 在独立 MySQL 实例执行异机恢复，而不仅是同库隔离前缀恢复。
4. 恢复后运行 `check:mysql`、`check:migration-integrity`、登录与核心业务冒烟。
5. 记录真实 RPO/RTO、值班升级链和定期演练窗口。
