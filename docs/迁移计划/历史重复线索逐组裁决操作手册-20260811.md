# 历史重复线索逐组裁决操作手册

## 1. 目的与边界

本手册只用于 `ISSUE-006/MIG-0125/DB-015` 的 42 组历史重复线索裁决。工具读取当前 MySQL 和规范化报告，不自动选择主记录、不修改线索、不删除记录，也不调用模型。旧自动物理合并和独立模型改名入口已经失败关闭。

当前基线为线索名 9 组/25 条、公司名 33 组/82 条，共 42 组/107 次记录引用、82 条唯一线索；其中 25 条线索同时出现在名称组和公司组，必须检查跨组决定是否一致。

## 2. 生成受限裁决底稿

先生成最新规范化报告，再生成 0600 裁决底稿：

```bash
npm run audit:mysql-normalization
npm run prepare:lead-duplicate-dispositions
```

底稿默认位于 `.runtime/migration-decisions/lead-duplicate-dispositions.json`。文件包含业务名称和稳定 UUID，只能交给获授权的业务负责人，不得粘贴到工单、聊天、日志或公开仓库。工具发现已有底稿时默认拒绝覆盖；只有确认原底稿全部为 `pending` 时才可运行：

```bash
npm run prepare:lead-duplicate-dispositions -- --replace-pending
```

一旦任一组已填写决定，生成器会拒绝覆盖，避免丢失审批。

## 3. 每组允许的决定

- `merge`：确认属于同一业务主体。`canonicalLeadId` 必须是组内记录；`mergedLeadIds` 必须精确等于组内其余记录。形成决定后仍须先运行执行预览，只有正式 apply 命令才会落账。
- `keep-separate`：确认记录虽然名称或公司名相同，但属于不同主体，应分别保留。
- `exception`：当前证据不足或存在经批准的历史例外，暂不合并；理由必须写明后续责任边界。
- `pending`：尚未裁决。严格门禁一定失败。

每个非 `pending` 组必须填写不短于 10 个字符的 `reason`、至少 2 个字符的 `approvedBy`、合法 ISO 时间 `approvedAt`，并把 `decisionRevision` 设置为正整数。不得修改 `groupId`、字段、规范化键、记录 ID/原值、行指纹、基线报告 SHA-256 或五项 safeguard。

## 4. 验证

编辑过程中运行预览验证：

```bash
npm run validate:lead-duplicate-dispositions
```

全部完成后运行严格验证：

```bash
npm run validate:lead-duplicate-dispositions:strict
```

严格验证会重新读取 MySQL 全行快照并阻断以下情况：少组/多组、记录集合变化、名称或公司值变化、任一行指纹漂移、审批不完整、主记录不在组内、合并范围不完整、同一重叠主体被指向两个不同主记录，以及“合并”和“分别保留”互相矛盾。当前 42 组仍为 `pending`，严格命令按设计退出 2，数据库写入为 0。

## 5. 执行与回滚边界

可回放事务执行器已经就绪，但在全部 42 组完成审批前会以退出码 2 失败关闭：

```bash
npm run apply:lead-duplicate-dispositions:preview
npm run apply:lead-duplicate-dispositions
```

预览始终零数据库写入。正式命令会在同一个 MySQL 事务中锁定全部受影响 Lead、复核全行指纹与决定文件 SHA-256，然后执行以下动作：

1. `merge` 只把从记录标记为 `已合并`，不物理删除；原行完整快照进入逐组 Issue，来源键并入主记录；
2. 评分任务、Pipeline Item、Entity Match 和 `lead_reserve.imported_lead_id` 精确迁移到主记录；评分任务或储备映射发生主键/唯一语义冲突时整事务回滚；
3. 已转项目线索若参与合并，必须自身就是该连通组主记录；同组出现多个项目归属时拒绝执行；
4. 每个从记录写入 `migration_entity_mappings`，每组写入 Issue，并追加 Run 和安全审计；相同决定文件可幂等复验，不同哈希不得复用同一决定集；
5. 在线列表、Radar、公开情报和人工复核不再把 `已合并` 记录当成活动候选，旧 Lead ID 的详情和转项目入口解析到主记录。

`accept:lead-duplicate-apply` 已在真实 MySQL 事务中构造两条夹具 Lead 及四类引用，验证引用各迁移一次、原行保留、来源键合并、Run/Issue/Mapping/Audit 原子落账，随后整体回滚并确认正式数据库写入为 0。

正式执行后运行：

```bash
npm run check:mysql-normalization
npm run accept:migration-business-invariants
npm run check:migration-integrity
```

规范化审计会排除已合并从记录，并只在 Run、Issue、稳定组 ID、字段、类型及规范键哈希一致时认可 `keep-separate/exception`；未裁决或账本漂移仍阻断。若最终存在获批的活动同名主体，就不能恢复“名称本身唯一”的索引，必须保留实体解析门禁；只有活动同名组为零时才可另建只前进唯一约束迁移。
