# 目标 Linux 单服务现场取证手册

本手册用于在真实部署主机上证明迁移后的项目只运行一个业务服务，而不是用开发机进程截图替代生产证据。取证只读取 systemd、cgroup、监听端口、timer、cron、Docker/Podman 运行清单、Nginx、运行环境文件权限和健康接口；不执行数据库写入，不调用模型，不生成 PPT，也不生成尽调、提案、Q&A 或合规性说明报告。

## 1. 运行命令

代码合入前执行纯静态契约检查：

```bash
npm run accept:target-single-service-evidence
```

部署脚本启动唯一服务并通过健康检查后，自动执行目标机只读取证：

```bash
npm run capture:target-single-service-evidence
```

现场报告写入 `.runtime/migration-evidence/target-single-service/live-report.json`，目录权限为 0700、文件权限为 0600。报告不读取或保存数据库、模型、IM 或 Cookie 密钥，也不保存主机名、machine-id、PID、cgroup 路径、命令行、环境变量值或业务数据；主机身份仅保留 SHA-256，便于区分不同取证节点。

## 2. 失败关闭条件

- `cybernaut-app.service` 不是 active/running/enabled，或没有有效 MainPID/cgroup；
- systemd 未设置 `KillMode=control-group`、MemoryMax、CPUQuota 或 TasksMax；
- systemd 未在唯一 `ExecStart` 前配置编译后的 `singleServicePrestart.js` `ExecStartPre`，未将其证据目录收口到私有状态目录，或缺少 `RestartPreventExitStatus=2 78` 与 300 秒/5 次启动限流；
- 3100 未在 loopback 监听，或监听进程不属于统一服务 cgroup；
- 3584/8121 任一旧端口仍在监听；
- 全量 systemd service/timer 清单中除 `cybernaut-app.service` 外仍存在以 `cybernaut`、`flue`、`radar`、`sbl` 或 `jedi` 命名的项目单元，包括 disabled 但 unit file 尚未移除的旧单元；
- `ps` 全量进程清单中存在统一应用、Radar/Flue 命令特征，或工作目录位于当前部署根的进程，但其 PID 不属于 `cybernaut-app.service` 的 cgroup；因此即使后台 Worker 使用通用脚本名且不监听端口，也会被识别。取证命令自身及其父进程会显式排除；
- root 或 `cybernaut-app.service` 运行用户的 crontab，以及 `/etc/crontab`、任意 `/etc/cron.d/*` 中仍存在 `daily_intake`、`batch_analyze`、`sync_radar` 或 Radar Python 任务；无法完整读取这些 cron 来源时同样失败关闭；
- Docker/Podman 中仍有项目业务容器或暴露 3100/3584/8121 的容器；
- Nginx 未通过语法检查、未启用 TLS 1.2/1.3、未代理到 3100，或仍包含 `/ai/api`、3584、8121；
- `.env` 存在 group/other 权限，或健康接口未返回 `cybernaut-app`。

部署会先停用已知旧单元，将 `/etc/systemd/system` 下六类旧 unit 文件备份到 `${APP_STATE_DIR}/migration-backups/systemd/<UTC时间>` 的私有目录，再从活动 unit 位置移除并执行 daemon-reload；未知改名单元不会自动删除，而会由全量清单门禁阻止上线，留给运维确认。

任何一项失败都会使部署退出非零。现场报告只保存单元、进程和异常进程数量，不保存 PID、命令行或 cgroup 路径。它只证明该次取证主机和该次部署状态；预生产与生产必须分别执行，不能用 macOS 本地结果代替。
