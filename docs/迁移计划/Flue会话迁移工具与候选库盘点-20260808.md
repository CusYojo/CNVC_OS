# Flue 会话迁移工具与候选库盘点（2026-08-08）

## 1. 当前结论

Flue SQLite→MySQL 会话迁移程序已经完成并通过隔离、幂等和内容级冒烟。当前发现的两个一致性备份候选源已全部受控处置：空库应用为 0 业务写入；另一个库的 1 个会话/2 条消息经逐记录复核证明只是固定 AI 网关验收 fixture，无用户、项目或业务归属，已按 checksum 锁定的 `exclude-acceptance-fixture` 策略排除，业务写入为 0 并留存 warning 问题台账。

该候选内容不能替代目标部署机的完整资产盘点。生产 Flue 阶段仍需证明部署机不存在其他 `FLUE_DB_PATH`/`flue.db`；如发现其他库，必须取得一致性备份，并通过自动 `agent_id` 对应或经批准的显式映射/排除文件确认归属。

## 2. 迁移规则

1. 用户、项目、范围和标题的权威来源是已迁移到 MySQL 的 PostgreSQL 会话索引；Flue canonical stream 不用于猜测用户。
2. Flue 的权威消息源只读取 `flue_conversation_streams` 和 `flue_conversation_stream_batches`；`event_stream` 只用于运行观测，不作为对话真身。
3. 主 root conversation 合并到相同 `agent_id` 的目标会话；子任务/子会话使用确定性 UUID 建独立记录并继承同一用户、项目权限。
4. 会话和消息通过 `agent_conversation_source_mappings`、`agent_message_source_mappings` 保存来源键和规范化校验和，不再依赖一个 `legacy_source` 字段表达多来源。
5. 消息优先按来源映射去重，其次按 Flue external message ID，再按角色、文本、思考、首个工具参数/结果和毫秒时间的精确语义指纹合并；多个候选冲突时阻断，不猜测。
6. canonical batch、record ID、block delta、附件 chunk 必须连续；附件大小和 SHA-256 必须一致。附件引用进入消息 Part，原始字节必须在文件资产阶段完成复制后才能切流。
7. 思考、文本、工具调用、工具结果分别保存为 Message Part；无法直接显示的 compaction、settlement、child-session 等原始 JSON 保存在会话迁移元数据。
8. 未完成 assistant message 标记为 `interrupted`，错误完成标记为 `failed`；迁移不会恢复或调用旧 Flue 进程。
9. 路径或表名出现 Aipin 身份时直接拒绝；JW 本机 37 个 Aipin 会话不进入任何映射或目标表。

## 3. 工具与审计结构

```bash
# 只读预览，不写会话数据
npm run migrate:flue:preview -- --source /absolute/path/flue.db

# 归属无法自动匹配时，只允许使用审批后的映射文件
npm run migrate:flue:preview -- --source /absolute/path/flue.db --map /absolute/path/flue-map.json

# 预览无阻断问题后应用
npm run migrate:flue -- --source /absolute/path/flue.db --map /absolute/path/flue-map.json

# 仅对经复核且以文件/内容 checksum 锁定的验收 fixture 执行排除
npm run migrate:flue -- --source /absolute/path/flue.db --exclude-source /absolute/path/approved-exclusion.json

# 隔离幂等与内容级冒烟
npm run check:flue-migration
```

映射文件只接受目标会话 ID，不接受临时用户或姓名推断：

```json
{
  "instances": {
    "chat-example": "已存在的-agent_conversations-UUID"
  }
}
```

新增 MySQL 表：

- `agent_conversation_source_mappings`
- `agent_message_source_mappings`
- `migration_runs`
- `migration_issues`

预览报告包含源文件 SHA-256、Flue Schema、stream/batch/record/conversation/message/part/attachment 数量、规范化内容校验和、目标计划数量和阻断/警告清单。应用完成后从 MySQL 重新读取消息、JSON、Part 和时间，重新计算目标校验和；不以“SQL 执行成功”代替内容验收。

## 5. 验证结果

`check:flue-migration` 在独立临时用户、会话和 SQLite fixture 上连续应用两次。既有孤立 Agent 被补齐 1 个可见 chat 索引，主会话保持3条消息/7个Part；另一个从 Flue 新生成的子会话同时生成1个chat索引、1个Agent、1条消息/1个Part。已验证：

- 两次应用幂等；
- PostgreSQL/Flue 精确重复消息合并为同一目标消息；
- 文本、思考、工具调用和结构化工具结果内容一致；
- 附件 chunk 大小和 SHA-256 校验、附件引用保留；
- 未完成消息保存为 `interrupted`；
- 孤立 Agent 和新生成子会话都能从用户可见列表索引恢复，chat/agent 的用户、项目、标题和 scope 一致；
- Agent 允许128字符外部会话ID，旧 chat 索引只有64字符；超长值不截断、不写碰撞值，只由共享会话UUID绑定；
- 源/目标规范化内容 checksum 一致；
- 测试用户、会话、消息、来源映射、运行记录和临时文件全部清理。

2026-08-10 内容级门禁增强：原合并后重排仅使用 `created_at,id`，同一毫秒消息会受随机 UUID 影响；现固定为 `created_at,sequence,id` 并直接断言 user→complete assistant→interrupted assistant 的 0/1/2 顺序。报告同时核对源/目标内容 checksum 两次相等且跨应用稳定，逐 Part 核对 3 个 text、1 个 reasoning、1 个 attachment、1 个 tool_call 和 1 个 tool_result，附件容量/摘要及工具输入输出一致。证据保存于 `.runtime/migration-evidence/flue-content-verification/report.json`，权限 0600 且不保存正文、路径或合成身份。

2026-08-11 可见性与跨源门禁增强：迁移器现在在同一事务内维护 `chat_conversations` 和 `agent_conversations`，验证阶段逐会话复核成对关系；失败测试留下的临时来源报告也按临时目录、报告 SHA 和文件名清理，不再污染正式来源清单。`audit:conversation-migration-content` 聚合 PostgreSQL dump、Flue、JW 处置报告和全目标 MySQL，核对消息/Part 顺序、状态、跨源映射、任务绑定和聚合内容 SHA；报告不保存正文、业务 ID 或源路径。当前本地证据就绪，但生产盘点未批准，严格生产门禁退出2。

当前 MySQL 有74张目标表、124条外键；最新业务不变量和状态机审计均为0违规。

## 6. 剩余阻断

1. 需要在目标部署机完成 Flue 资产搜索并留存“无其他生产 `FLUE_DB_PATH`/`flue.db`”证据；如有其他库，需取得一致性备份、文件哈希和停写水位。
2. 如发现新的业务会话源，需让生产 Flue instance ID 与 13 条会话索引自动匹配；无法匹配的每一条都必须由业务负责人批准显式映射、checksum 锁定排除或只读归档。
3. 有附件的生产源还需完成字节资产目标路径、权限、manifest 和恢复抽样，只有引用进入 MySQL 不足以通过 FILE 门禁。
4. 实际生产应用后才能勾选 `MIG-0715`、`CHAT-019/020` 和对应数据核验门禁。
