# 生产源资产盘点与批准

## 目的

本地已对 checksum 锁定的 PostgreSQL dump、两个 Flue 候选库和 JW 排除源完成核验，但这不能自动证明目标生产机不存在其他 `flue.db`、PostgreSQL dump 或未盘点源文件。`productionSourceInventoryReady` 因此必须由目标机扫描和明确批准证据关闭。

## 执行方式

先在目标机只读生成候选报告：

```bash
npm run inventory:production-sources -- \
  --scan-root /data \
  --scan-root /var/lib/cybernaut-app \
  --postgres-dump /approved-backup/cybernaut_mvp_dump.sql \
  --flue-source /approved-backup/sbl_code-data-flue.db \
  --flue-source /approved-backup/sbl_code-runtime-flue.db \
  --environment production
```

工具会递归扫描显式根目录，计算已声明源的 SHA-256，并列出未声明的 `flue.db`，以及无论是否改名、只要扩展名为 `.sql/.dump/.backup/.pgdump` 且文件头符合 PostgreSQL plain/custom dump 的候选源。必须且只能提供一个 `--postgres-dump`；重复参数会失败关闭。扫描根和已声明源本身若为符号链接会直接拒绝，目录内符号链接会记录并返回退出码 2；重叠扫描根只统计一次文件。默认最多扫描 200,000 个唯一普通文件，只能用 `MIGRATION_SOURCE_SCAN_MAX_FILES` 显式调整。

`accept:production-source-inventory` 使用独立临时目录验证改名 dump 检出、入口符号链接拒绝、重复 dump 参数拒绝、重叠根去重和测试输出不能生成批准报告；不会读取生产路径、覆盖当前候选报告或写数据库。

候选报告位于：

```text
.runtime/migration-evidence/production-source-inventory/candidate.json
```

数据负责人核对扫描根、主机身份、dump/Flue 哈希和 `unexpectedSources=0` 后，在同一主机上以稳定身份再执行：

```bash
npm run inventory:production-sources -- \
  --scan-root /data \
  --scan-root /var/lib/cybernaut-app \
  --postgres-dump /approved-backup/cybernaut_mvp_dump.sql \
  --flue-source /approved-backup/sbl_code-data-flue.db \
  --flue-source /approved-backup/sbl_code-runtime-flue.db \
  --environment production \
  --approve \
  --approved-by data-owner-stable-id
```

批准报告以 0600 权限写入：

```text
.runtime/migration-evidence/production-source-inventory/report.json
```

## 严格门禁

`audit:migration-reconciliation` 仅在以下条件全部成立时设置 `productionSourceInventoryReady=true`：

- 报告环境为 `production`，并有主机身份、生成时间和非空扫描根；
- PostgreSQL dump SHA-256 与当前迁移基线一致；
- Flue 源 SHA-256 集合与已核验候选源完全一致；
- `unexpectedSources=0`且无跳过的符号链接；
- `approved=true` 且 `approvedBy` 为非空稳定身份。

当前工作区没有生产批准报告，因此该门禁正确保持阻断。
