# 历史源数据缺口裁决手册

## 当前范围

当前严格迁移门禁仍有两类无法从现有介质恢复的源数据缺口：

| 领域 | 数量 | 当前安全状态 | 可批准结论 |
|---|---:|---|---|
| `lead_reserve.detail_json` | 97 | 原行保留、未导入、`source_missing`、逐条问题台账完整 | `approved-permanent-quarantine` |
| 旧 AI 产物源字节 | 7 | 归属/任务/元数据已恢复，在线隐藏，`archived=1/failed` | `approved-permanent-archive` |

7 个 AI 产物按任务类型和格式汇总为：合规性说明 DOCX 2、Markdown 2；投资提案 DOCX 3。它们都属于用户要求不执行生成测试的类别，但“不测试生成”不等于“批准历史源字节永久缺失”，两项结论必须分开。

17 个项目原件已有独立精确批准台账，本手册不重新打开该决定，也不把它们计入当前缺口。

2026-08-11 的扩展只读复核已同一次覆盖 Desktop、Documents 和 Downloads 三个标准用户资料根。发现器仍按精确文件名、dump 身份、任务/用户/项目归属、预期字节数、格式签名、OOXML CRC 和唯一 SHA-256 验证候选；7/7 仍为 `not_found`、0 可恢复、0 写库。私有证据只保存根路径哈希，不保存用户绝对路径。因此当前不再把“常用本机目录漏扫”视为可恢复候选；若仍要恢复原字节，需提供旧生产机或独立备份介质的授权源根。

## 私有决策底稿

生成命令：

```bash
npm run prepare:source-gap-dispositions
npm run validate:source-gap-dispositions
```

底稿默认保存在 `.runtime/migration-decisions/source-gap-dispositions.json`，权限为 0600。文件对 97 条储备记录和 7 个 AI 产物逐条保存稳定 ID、必要审阅字段和当前行指纹，并为两个领域分别绑定完整集合 SHA-256。报告和控制台只输出数量，不输出 ID、文件名或审批身份。

底稿已存在时默认拒绝覆盖。只有两个领域都仍为 `pending` 且没有任何审批字段时，才能执行：

```bash
npm run refresh:source-gap-dispositions
```

源文件若后来恢复，应先执行恢复工具，再刷新 pending 底稿；记录数量或任何指纹变化都会使旧底稿失败，不能继续沿用旧批准。

## 审批填写

只允许修改两个领域对象中的以下字段，不得删除、增加或改写 `records`、`count`、`baselineSha256`：

```json
{
  "disposition": "approved-permanent-quarantine 或 approved-permanent-archive",
  "rationale": "不少于 12 个字符的项目专属理由",
  "approvedBy": "稳定审批身份",
  "approvedAt": "ISO-8601 时间"
}
```

- `leadReserve` 只接受 `approved-permanent-quarantine`。
- `aiArtifacts` 只接受 `approved-permanent-archive`。
- “已跳过报告测试”“本地找不到”“文件不重要”等不能被工具自动推导为批准。
- 审批只承认缺口并保持隔离/归档，不制造 `detail_json`、文件字节、哈希、正文或恢复成功假象。

完成后执行：

```bash
npm run validate:source-gap-dispositions:strict
```

当前严格命令应返回退出码 2，因为两个领域都是 pending。只有精确集合、全部指纹、允许的结论、理由、审批身份和时间共同通过时才返回 0。

## 当前安全边界

`accept:source-gap-dispositions` 以真实 MySQL 只读基线和私有临时底稿验证：pending 严格阻断、精确批准夹具通过、批准后不可刷新覆盖、指纹漂移拒绝、把“排除测试”写成处置结论会拒绝，前后迁移 Run/Issue 数量与两个领域集合 SHA 完全一致，数据库写入 0。

严格校验通过后，先预览正式台账应用：

```bash
npm run apply:source-gap-dispositions:preview
```

预览会再次读取真实 MySQL、核对两个完整集合、每行指纹、既有批准台账和私有决策文件 SHA，数据库写入 0。只有预览数量、结论和审批身份复核通过后，才可执行：

```bash
npm run apply:source-gap-dispositions
```

首次应用在同一事务内写入 2 条成功迁移 Run 和 104 条逐项 Issue；再次执行必须识别完整相同台账并写入 0。任何部分台账、集合漂移或 payload 与批准指纹不一致均失败关闭。Run 报告与文件证据不保存审批身份、文件名或业务正文；正式 Issue 保存审批身份、时间、理由、结论和必要指纹，但绝不保存缺失正文、缺失文件内容或伪造哈希。

验收通过真实目标 MySQL 事务探针实际插入 2 个 Run 和 104 个 Issue 后整体回滚，验证约束、字段和 SQL 路径，前后正式 Run/Issue 数量不变、数据库提交写入 0。当前正式底稿仍是 pending，因此正式 preview/apply 都会拒绝；在收到两个领域明确批准前 `MIG-0507/0407/0723` 和 `DATA-005/007/018/023` 保持未完成。
