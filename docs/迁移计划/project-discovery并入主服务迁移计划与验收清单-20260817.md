- 切换和旧服务下线已经完成；当前只保留只读回滚备份与观察期事项。

### 1.2 目标架构

主服务成为唯一业务入口和唯一在线事实源：

```text
外部信源
  ↓
主服务 Runtime Job / 单次采集适配器
  ↓
sbl_radar_raw_events（不可变原始事件）
  ↓
sbl_radar_candidates（当前候选投影）
  ↓
主体识别、AI 审核、人工复核
  ↓
sbl_leads（公共线索池）
```

目标状态必须满足：

- 不存在独立 FastAPI 雷达进程；
- 不监听 8121 端口；
- 不再配置或读取 `RADAR_BASE_URL`；
- 不存在独立 Radar cron、timer 或常驻采集线程；
- MySQL 是候选、状态、来源、任务和运行记录的唯一在线事实源；
- Python 如需保留，只能作为主服务启动的单次采集适配器，不得监听端口或自行调度；
- 原 `project-discovery/` 在观察期结束后删除。

## 阶段 P3：采集器内置

目标：废弃独立常驻进程，同时保留全部采集能力。

## 5. 回滚方案

### 5.1 回滚触发条件

满足任一条件立即评估回滚：

- 主服务 Radar API 持续不可用超过 10 分钟；
- 关键来源候选缺失超过 1%；
- 候选重复率超过 0.5%；
- 微信群 Push 持续失败或发生不可恢复消息丢失；
- 五类任务中关键任务连续失败 3 次；
- 数据写入出现来源键冲突、孤儿事件或不可解释覆盖；
- 正式线索同步出现批量错误写入。

### 5.2 回滚步骤

1. 禁用主服务 Radar 写任务，保留 MySQL 数据不删除。
2. 恢复上一版主服务配置和 `RADAR_BASE_URL`。
3. 重新启动旧 `cybernaut-radar.service`。
4. 恢复旧同步 timer。
5. 验证 8121 健康检查和候选查询。
6. 根据切换水位补偿回滚期间产生的增量。
7. 记录回滚原因和数据差异，修复后重新进入影子运行。

回滚不得删除已迁移的 MySQL 原始事件；后续通过来源键和内容哈希幂等重放。
