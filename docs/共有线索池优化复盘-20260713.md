## 一、部署拓扑（先搞清楚，否则白改）

**血泪教训：第一轮花了大量时间改代码，结果用户根本看不到，因为改错了地方。**

- **前端**：`npx vite build` → 产物落 `dist/`（带 hash 的 js，如 `index-XXXX.js`）→ **nginx :5180 静态托管** `/data/cybernaut-mvp/dist`。
  - nginx conf: `/etc/nginx/conf.d/cybernaut.conf`，`root /data/cybernaut-mvp/dist`，`/assets/` 走 `expires 7d immutable`，`index.html` 走 `max-age=0`。
  - **改前端必须 `npx vite build`，nginx 自动读新 dist（无需 reload）。只改 src/ 不 build = 用户看不到。**
  - 用户访问 URL 是 `http://101.126.131.28:5180/sourcing`（不是 5173/8180，那些是别的项目的 vite dev server）。
- **后端**：`server/src/` → `npx tsc -p server/tsconfig.build.json` → 产物落 `server-dist/` → **裸 node 进程** `node server-dist/index.js` 跑在 :3100（不是 pm2！pm2 里的 cynthia-backend 是别的项目）。
  - 重启后端：`pkill -9 -f "node server-dist"; sleep 1; (nohup node server-dist/index.js > logs/server.log 2>&1 &)`
  - 日志在 `/data/cybernaut-mvp/logs/server.log`。
- **数据库**：Postgres，连接走 `server-dist/db/client.js` 的 pool（`DATABASE_URL` 或默认）。快速查库：写 `.mjs` 用 `import {pool} from "/data/cybernaut-mvp/server-dist/db/client.js"` 然后 `node xxx.mjs`。

**编辑远端文件的正确姿势**（本地 patch/read_file 工具读不到远端）：
- 用 `write_file` 在本地 `/tmp/xxx.py` 写一个 python 脚本（内容是 `pathlib` 读文件 + `str.replace` + 断言 `assert old in s` + 写回）
- `scp /tmp/xxx.py root@host:/tmp/` 然后 `ssh ... 'cd /data/cybernaut-mvp && python3 /tmp/xxx.py'`
- 每个 replace 都带 `assert old in s, "描述"`，匹配不上立即报错，不会静默改错。

## 二、按时间顺序的问题与解法

### 问题1：分页——"公共池只显示 50/看不见分页器"
- **表象**：列表只有 50 条，没有分页控件。
- **真因**：`listLeads()` 后端写死 `.limit(100)`；前端一次性 `.map` 渲染，无分页 UI。而当时看到的"50 条"其实是 **mock 种子数据**（`src/mock/data.ts`），因为前端 dist 是旧的、且 zustand 初始值用 mock。
- **解法**：
  - 后端 `listLeads({page,pageSize})`，SQL `LIMIT/OFFSET`，返回 `{list,total,page,pageSize,totalPages}`。`total` 用**独立 `count(*)` 查询**，不要用 `count(*) over()`（offset 越界时窗口函数不计算 total，返回 0）。
  - route `GET /leads` 用 zod 校验 `page/pageSize`（pageSize max 100）。
  - 前端 store 加 `leadPagination` + `fetchLeads(page,pageSize)` action；SourcingPage 加分页器 UI + `useState(page)` + useEffect 翻页。
  - 翻页后 `window.scrollTo` 平滑滚到表头。

### 问题2："统计显示 0/翻页很慢，要用 Redis 吗？"
- **表象**：顶部"公共池线索"统计显示 0；翻页/切页等好几秒。
- **真因A（统计）**：顶部卡片用 `publicLeads.length`（当前页 50 条），应该用 `leadPagination.total`（全量 300）。
- **真因B（慢）**：**不是网络，也不需要 Redis**。`listLeads` 用 `.select()` 拉全字段，每条 leads 的 jsonb 大字段（`scoring`~16KB、`radar_profile`~8-37KB、sources、funding_rounds）全序列化，50 条 = 1.1MB JSON。`GET /leads` ttfb 15s，纯序列化开销。
  - **诊断关键**：node 里直接调 `listLeads()` 只要 2ms（SQL 15ms），但 HTTP 层 ttfb 6-15s → 瓶颈在响应体序列化+传输，不是 SQL、不是 Express、不是连接池。
  - 附带发现：这台机器 IPv4 `127.0.0.1` 比 IPv6 `[::1]` 慢（hello world curl：IPv4 380ms vs IPv6 90ms），但不是主因。
- **解法**：
  - `listLeads` 改成**只 SELECT 列表展示需要的列**（id/name/company/industry/source/poolStatus/score/summary + createdAt），**排除所有 jsonb 大字段**。响应 1.1MB → 58KB，ttfb 15s → 2s。
  - 详情弹窗需要的全字段（scoring/sources/funding_rounds/radar_profile）走**新增的 `GET /leads/:id` 详情接口**，按需拉单条。
  - 前端 `hydrateFromServer` **不再拉 /leads**（原来 8 个接口并发，leads 那条 15s 阻塞整个首屏），leads 完全交给 SourcingPage 的 `fetchLeads` 单独拉。
  - store 加 `fetchLeadDetail(leadId)` action，详情弹窗 onClick 时拉全字段并 setSelected。

### 问题3："信源只有 36氪，机构/高校/创投/论文都没了"（渠道全变"新闻"）
- **真因**：优化问题2时，为省带宽把 `radar_profile` SQL 切成了 `radar_profile->'profile'`（扁平化），**丢掉了 `channel` 字段**。而后端 `enrichLead` 靠 `radarProfile.channel` 定渠道，读不到就 fallback 成"新闻"。
- **解法**：列表 SQL 的 radar_profile 改用 `jsonb_build_object('profile', ..., 'channel', ..., 'sourceName', ..., 'sourceGroup', ...)`，**保留 channel 且与详情接口结构同构**（否则 setSelected(列表lead) 后 Drawer 按嵌套结构访问会崩）。大小仍 <1KB。
- **教训**：**精简 jsonb 字段时，前端所有读该字段的路径都要过一遍，结构必须与详情接口同构。** 扁平化会连锁引发渠道错乱、详情弹窗崩溃、评分丢失。

### 问题4："选渠道选不了/筛选没结果"
- **真因**：渠道筛选是**前端本地 `.filter(当前页50条)`**，选"高校公众号"时若当前页正好没有就显示空；且和服务端分页冲突。
- **解法**：改**服务端渠道过滤**。`listLeads({channel})` 加 `WHERE radar_profile->>'channel' = $channel`（雷达数据的真实渠道值正好是筛选项）。route 加 channel query。前端 select onChange 时 `setChannel + setPage(1)`，useEffect 依赖加 channel，`fetchLeads(page,50,channel)`。去掉前端本地 channel 过滤。
- 后续需求：把 "36氪" 也加进渠道下拉（`leadChannels` 数组首位），因 36氪 数据 `radar_profile.channel='36氪'`，服务端过滤直接生效。

### 问题5："领取失败：Cannot read properties of undefined (reading '0')"
- **真因**：`convertLead` 访问 `lead.fundingRounds[0]`，但列表接口精简掉了 fundingRounds → undefined → `undefined[0]` 崩。同类还有 `lead.riskTags.length`、`lead.highlights`、`lead.sources.map`、`lead.scoring`。
- **解法**：`convertLead` 开头先 `fetchLeadDetail(leadId)` 拉完整 lead，所有数组字段带 `?? []` 兜底，`(lead.fundingRounds ?? [])[0]?.valuation`。
- 附带修：领取后 `addFile` 调 `/projects/:id/files`（404），后端实际是 `POST /projects/files`（body 带 projectId）——端点路径对不上。

### 问题6："AI 评分失效/点了没结果返回"
- **真因**：`GET /leads/:id/score` 的状态判断是 `scoring ? 'done' : ...` —— 只要 lead 有**任何** scoring 就返回 done。而线索**入池时就写了结构化 scoring**（registry/股东/融资，但**没有** AI 分析的 dimensions/verdict/overall_comment）。所以前端第一次轮询就被误判 done，AI 深度分析被"短路"，显示的还是入池老数据。
- **解法**：`GET /score` 状态判断改成**内存态优先 + 只认 AI 产物**：
  ```
  const hasAiScoring = !!(scoring && scoring.dimensions)   // AI 深度分析产物特征=有 dimensions
  if (st?.status === 'running') status = 'running'
  else if (st?.status === 'failed') status = 'failed'
  else if (st?.status === 'done' || hasAiScoring) status = 'done'
  else status = 'idle'
  ```
- **验证**：Flue :8791 `/workflows/score-project?wait=result` 单独 curl 能返回真评分（total/verdict/dimensions），耗时~40s-170s。修复后触发→稳定 running 170s→done，total 从占位更新为真实分。
- **教训**：**"有数据"≠"任务完成"。异步任务的完成判定要看任务产物的特征字段（dimensions），不能只看字段是否非空——尤其当同名字段在不同阶段被写入不同内容时。** 内存状态机（scoreStatus Map: running/done/failed）必须优先于 DB 快照。

### 问题7："分析成功但 AI 评分没更新分数"
- **真因**：runScore 评分完成后调 `updateLeadInStore(fresh.id, fresh)`，而这个 `updateLead` action 实际会发 **`PATCH /leads/:id`** 请求——**后端根本没这个路由** → 404 → catch 静默吞掉 → store 里的 score 从没更新 → 界面停在旧分数。（DB 里 score 其实早就对了，saveLeadScoring 正常。）
- **解法**：store 加纯本地合并 action `mergeLeadLocal(leadId, patch)`（只 `set`，不发请求）；runScore 完成 + 超时兜底两处改用它。
- **教训**：**区分"改后端并同步"的 action（发 PATCH）和"仅更新本地视图"的 action（纯 set）。** 拿一个会发请求的 action 去做纯本地状态更新，请求失败会静默丢掉更新。catch 块里至少要 log 或 toast，不要空 catch。

### 问题8：每日业务链（36氪入池 + 其他信源抓取 + AI分析）
- **要求**：36氪 走数据库每天放 50 个；机构/高校/创投/论文 走信源抓取；8 点更新→AI分析→前端显示。
- **现状核查**：cron `0 8 * * *` 跑 `run_daily_intake.sh` → `daily_intake.mjs`。三段都有，但：
  - AI 分析段有个无害 bug：重复 `await pool.end()` → "Called end on pool more than once"。
  - **缺口：雷达抓取（sync-radar）的线索没走 AI 分析**——分析只对 36氪入池的 insertedIds 触发。
- **解法**：
  - `sync-radar` 返回 `createdIds`（收集 createLead 返回的 id）。
  - daily_intake.mjs 抽出统一 `analyzeLeads(base,token,ids,tag)` 函数（小并发 SCORE_CONCURRENCY=2，轮询到 done/failed），36氪 和 雷达 两批都调它。
  - 修 pool.end 重复。
- **重大事故 + 教训**：改 daily_intake.mjs 时用 `s.index('await pool.end();')` 定位截断点，结果命中的是**第 20 行**（`if(!rows.length){...await pool.end()}`）而非预期的主流程末尾那个，把整个入池主循环删了。**且当时没有 .bak 备份**，只能凭对话历史 + 重新探 `lead_reserve.detail_json` 真实结构（`name/companyName/oneWord/intro/industryList[].name/business.{regLocation,shareholder[],estiblishTime,legalPersonName}/financingList[].{roundTxt,amount,investorList}`）重建整个文件。
  - **铁律：改关键脚本前先 `cp x x.bak-$(date +%s)`。用 `str.index` 定位时，若目标字符串在文件里出现多次，必须用更长的唯一上下文，或 `rindex`，或数出现次数校验。**

## 三、这个项目的可复用心法（下次接手/接类似项目）

1. **先确认"用户看的到底是哪个进程/哪份产物"**，再动手。多项目混部一台机器时，端口/pm2/nginx 都可能指向别的项目。核对链路：浏览器URL → nginx → 静态dist/反代端口 → 进程 → 源码目录。
2. **列表接口精简 jsonb 大字段是对的**（性能），但要配套：(a) 详情接口 `GET /:id` 补全字段；(b) 前端所有消费该字段的地方（列表渲染、领取、评分、详情弹窗）都要用详情接口或带兜底；(c) 精简后的结构要与详情接口**同构**。
3. **异步任务状态**：用内存状态机（Map: running/done/failed）作为唯一真相源，DB 快照只做补充判定，且要看**产物特征字段**而非"字段是否存在"。
4. **前端 store action 分两类**：会发后端请求的（updateXxx→apiPatch/apiPost）vs 纯本地视图更新的（mergeXxxLocal→set）。别混用。空 catch 是 bug 温床。
5. **改远端文件**：write_file→scp→ssh python，每个 replace 带 assert；改关键脚本先备份。
6. **验证要用真数据真接口**：写 `.mjs` 直连 pool 查库；写 `.py` 用 urllib 打真 API（中文参数记得 `urllib.parse.quote`，别在 shell 里裸传中文 URL）；能用 browser 工具就实际点一遍复现用户操作。
