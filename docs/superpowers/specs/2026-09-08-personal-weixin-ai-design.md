# 个人微信 AI 接入与管理员审批设计

## 目标与范围

为约 10 至 20 名内部用户提供各自独立的微信 AI 入口。每名用户登录平台后生成自己的微信 iLink 授权二维码，用本人微信扫码，管理员批准后启用。每个人拥有独立机器人连接、平台身份映射和 Agent 会话，消息、项目权限及知识库权限互不串用。

本次复用已有 `im_bots`、`im_bot_bindings`、`agent_conversations` 和审计表，不新增数据库表或字段，不引入绑定码。功能包含普通用户扫码入口、管理员审批、个人机器人生命周期、消息隔离、重新连接、审批结果展示及跨主机单实例轮询。

## 角色与权限

- 状态为“启用”且拥有非 `system_admin` 有效业务角色的平台用户，可以创建和管理自己的微信 AI 入口。
- 纯“系统管理员”账号负责配置和审批，不能借个人机器人绕过现有公司知识库业务权限。
- “系统管理员”“运营管理员”或具备 `im.manage` 权限的账号可以审批、拒绝、停用和查看全部个人机器人。
- 普通用户只能读取自己的机器人摘要、审批状态和连接状态，不能读取机器人令牌、微信内部标识或其他用户配置。
- 审批只启用身份接入，不授予任何新业务角色。项目、知识库、文件和 AI 工具继续按机器人所属平台用户实时鉴权。

## 用户流程

1. 业务用户登录平台，在个人设置打开“我的微信 AI”。
2. 用户点击“生成连接二维码”，后端创建仅属于当前登录用户的短时扫码会话，返回约 5 分钟有效的二维码。
3. 用户使用自己的微信扫码并确认。后端收到 `ilink_bot_id`、`ilink_user_id` 和机器人令牌后加密保存凭据，创建或更新该用户唯一的个人微信机器人。
4. 首次扫码后机器人保持 `enabled=false`，`connectionStatus=connected`，审批状态为 `pending`。页面提示“已连接，等待管理员审批”。审批前不启动该机器人的消息轮询。
5. 管理员在“系统管理 → IM 机器人 → 接入审批”核对平台用户、部门、业务角色、扫码时间和机器人标识摘要，填写至少 2 个字的理由后批准或拒绝。
6. 批准时创建该平台用户的全局 Agent 会话和唯一有效 `im_bot_binding`，将机器人设置为启用并标记 `approved`。
7. 拒绝时保持机器人停用并标记 `rejected`，凭据仍加密保存，用户可以查看理由后重新扫码申请。
8. 用户在自己的微信机器人窗口发送消息、文章链接或文件，后端只使用该机器人所属用户和绑定会话处理。

## 现有数据结构的使用

不增加迁移。个人机器人继续保存在 `im_bots`：

- `created_by`：个人机器人的平台用户，也是唯一所有者。
- `credential_ciphertext`、`credential_fingerprint`、`credential_hint`：沿用现有加密凭据机制。
- `enabled`：只有管理员批准且用户仍具备业务角色时为 true。
- `connection_status`：微信扫码连接状态，和审批状态分开。
- `config`：保留现有 `accountId`、`accountUserId`，增加 `ownershipMode='personal'`、`approvalStatus='pending|approved|rejected'`、`requestedAt`、`reviewedAt`、`reviewedByUserId`、`reviewReason`。列表接口只返回允许公开的审批字段。
- `version`、`updated_by`、`updated_at`：用于乐观锁和变更追踪。

批准后复用 `im_bot_bindings`：

- `bot_id` 指向个人机器人。
- `user_id` 必须等于机器人的 `created_by`。
- `external_conversation_id` 使用 `${accountId}:${accountUserId}`。
- `conversation_id` 指向该用户专属的全局 Agent 会话。
- 每个个人机器人只允许一个有效绑定。

重新扫码更新同一用户现有的个人机器人，不创建第二个启用机器人。匹配顺序先按 `created_by + ownershipMode` 锁定，再更新凭据和账号标识；旧绑定在新的账号标识获批前保持停用，防止凭据与身份映射错配。

## 服务与接口

扫码服务增加个人模式，扫码会话在进程内短时保存，但会话绑定当前登录用户 ID，等待接口必须由同一用户调用。二维码本身不能指定其他平台用户。

普通用户接口：

- `POST /api/integrations/im/weixin/self/login/start`：创建当前用户的扫码会话。
- `POST /api/integrations/im/weixin/self/login/wait`：确认扫码并创建或更新当前用户的 pending 机器人。
- `GET /api/integrations/im/weixin/self`：读取自己的连接和审批摘要。
- `POST /api/integrations/im/weixin/self/disconnect`：停用自己的机器人和绑定，不删除审计及历史会话。

管理员接口：

- `GET /api/integrations/im/weixin/access-requests?status=pending|resolved`：分页读取个人机器人审批列表。
- `POST /api/integrations/im/weixin/access-requests/:botId/resolve`：提交 `approved|rejected`、处理理由、预期版本和幂等键。

审批服务在数据库事务中锁定机器人，验证当前版本、状态、所有者和审批人权限。批准时创建或复用该所有者的个人全局会话，停用该机器人所有旧绑定，创建唯一有效绑定，再启用机器人并写审计。重复使用同一幂等键返回原结果；状态或版本冲突时不部分写入。

所有接口沿用现有登录、CSRF、Origin、输入校验、凭据加密和审计机制。公共响应不返回 `credentialCiphertext`、完整 `accountId`、`accountUserId` 或扫码内部状态键。

## 消息路由与会话隔离

个人机器人收到消息时执行固定校验：

1. 机器人必须 `enabled=true`、`connectionStatus=connected`、`ownershipMode=personal` 且 `approvalStatus=approved`。
2. 机器人的 `created_by` 用户必须仍为启用状态并具有有效业务角色。
3. 微信消息的 `from_user_id` 必须严格等于机器人 `config.accountUserId`。其他发送者只收到“该机器人仅供所有者使用”，不得创建会话、绑定或业务数据。
4. 有效绑定的 `user_id` 必须等于 `created_by`，`external_conversation_id` 必须匹配当前机器人账号和发送者。
5. 消息只路由到绑定中固定的 `conversation_id`。模型、前端和消息内容都不能修改用户或会话范围。

删除当前 `ensureInboundBinding()` 对陌生发送者自动建立管理员绑定的兜底行为。管理员已有的旧共享机器人保持原模式，不自动转换为个人机器人；个人机器人只走严格所有者路径。

重新扫码或重新审批后创建新的 Agent 会话，不继承不同微信身份或旧平台映射的历史。相同用户、相同微信身份的普通重连可以复用原会话，但必须通过服务端一致性校验。

## 跨主机单实例轮询

现有文件锁只能限制一台机器上的重复进程，无法阻止本地与服务器同时轮询并重复回复。微信桥接启动时增加 MySQL advisory lock，锁名由数据库名和微信桥接用途生成，并使用独占数据库连接持有。

只有获得数据库锁的实例启动全部微信机器人轮询；其他实例保持 standby 并定时竞争。连接断开、进程退出或服务关闭时锁自动释放或显式释放。文件锁可以保留为本机快速保护，但数据库锁是跨主机唯一性依据。该机制复用 MySQL，不新增表。

## 页面设计

个人设置增加“我的微信 AI”卡片：

- 未连接：显示“生成连接二维码”。
- 扫码中：显示二维码、剩余时间和取消按钮。
- 待审批：显示申请时间和“等待管理员审批”。
- 已批准：显示已连接、最近连接时间和“重新连接”“停用”操作。
- 已拒绝：显示管理员理由和“重新扫码申请”。

IM 机器人管理页面增加“接入审批”标签和待审批数量。列表显示平台用户、部门、业务角色、申请时间、连接状态和审批状态。审批详情不显示凭据；批准和拒绝均要求理由，并使用预期版本与幂等键。网络结果不确定时保留相同请求重试。

管理员原有“添加微信机器人”入口保留，用于旧共享机器人管理，并明确标注“管理员共享机器人”；普通用户只看到个人入口，不进入系统管理页面。

## 错误处理与生命周期

- 同一用户同时只能有一个扫码会话和一个个人机器人；重复点击返回当前扫码状态或现有机器人状态。
- 二维码过期后用户重新生成，不产生机器人记录。
- 扫码成功但凭据保存失败时返回失败，不展示已连接状态。
- 待审批期间再次扫码更新凭据并提升版本，原审批页面提交旧版本会冲突，管理员必须刷新后处理。
- 被拒绝或用户主动停用后不轮询；重新申请必须再次扫码。
- 用户被停用或失去全部业务角色后，轮询器跳过该机器人；管理员列表提示账号不可用。
- 审批批准后若创建会话或绑定失败，事务回滚，机器人继续 pending，不出现半启用状态。
- 普通用户无需寻找或添加公共机器人；二维码直接创建属于自己的微信 AI 入口。

## 审计与隐私

记录个人扫码确认、申请审批、拒绝、重新连接、停用、凭据替换、绑定建立和轮询领导权变化。审计包含操作者、机器人 ID、所有者、结果、理由和请求 ID，不保存二维码内容、机器人令牌、完整微信标识或消息正文。

个人页面及管理员列表对微信内部标识脱敏。日志沿用安全错误输出；任何异常不得输出凭据、二维码会话键或完整上游响应。

## 测试与验收

- 扫码测试：扫码会话绑定登录用户、过期、重复等待、用户 A 不能完成用户 B 的扫码会话。
- 个人机器人测试：首次创建 pending、重新扫码更新同一机器人、凭据保持加密、响应字段脱敏。
- 审批测试：权限、必填理由、版本冲突、批准事务、拒绝不启用、幂等重试和失败回滚。
- 隔离测试：A、B 分别进入独立 conversation；陌生发送者、错误微信身份和错误 binding 均被拒绝；不再创建管理员兜底绑定。
- 生命周期测试：用户停用、业务角色移除、主动停用、拒绝后重连和相同身份会话复用。
- 领导锁测试：两个模拟实例只有一个获得 MySQL 锁，领导连接释放后 standby 接管。
- 页面测试：二维码、倒计时、五种状态、审批列表、权限隐藏、提交锁定和不确定结果重试。
- 回归测试：管理员共享机器人、微信文章收录、知识库权限、项目待复核、文件消息和扫码凭据加密继续有效。

验收标准：至少两个不同平台用户各自扫码并经管理员批准后，能在各自微信窗口持续使用独立 AI 会话；任何跨用户消息、历史、项目和知识库访问均被拒绝；本地与服务器同时运行时一条微信消息只产生一次回复；全过程不新增数据库表或字段。
