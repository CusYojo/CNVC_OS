# FDE 立项后老板审批恢复设计

日期：2026-09-15

状态：已确认业务规则，待书面规格复核

## 背景

用户确认，FDE 投资项目从“立项”进入“尽调计划制定”必须经过老板审批。“老板”是业务概念，对应项目治理中配置的董事长或总裁，采用或签，任意一名有效审批人通过即可。

2026-09-14 的流程调整把该阶段审批配置误改为空数组。项目中心仍允许发起审批，后端解析得到空审批节点后读取首节点 `id`，触发 `TypeError` 和 HTTP 500，前端显示“服务不可用”。

## 最终业务规则

| 阶段流转 | 执行与审批规则 |
| --- | --- |
| 入库 → 立项 | 老板审批；项目董事长或总裁任意一人通过 |
| 立项 → 尽调计划制定 | 老板审批；项目董事长或总裁任意一人通过 |
| 尽调计划制定 → 尽调计划审核 | 投资项目组任意成员完成并提交计划 |
| 尽调计划审核 → 尽调 | 老板审批；项目董事长或总裁任意一人通过 |
| 尽调 → 内核 | 老板审批；项目董事长或总裁任意一人通过 |
| 内核 → 投决 | 财务 → 法务 → 老板，严格串行；每个职责节点内部或签 |
| 投决 → 打款 | 董事长 → 总裁，严格串行；两人分别通过 |
| 打款 → 投后 | 财务审批；已配置财务人员任意一人通过 |

本次只恢复“立项 → 尽调计划制定”的老板审批，不改变其他已确认规则。

## 目标

- 恢复“立项”阶段的 `boss` 审批职责。
- 发起该阶段审批时生成有效的董事长/总裁或签节点。
- 缺少有效董事长/总裁时返回明确的 409 业务错误，不返回 500。
- 申请人不能审批自己；排除申请人后必须至少有一名有效老板审批人。
- 新发起的审批使用新规则，已发起审批继续使用原有节点快照。
- 项目中心和审批中心展示同一条真实审批链。
- 对任何意外空审批节点增加防御，禁止再次访问 `undefined.id`。

## 非目标

- 不把尽调计划的编写权限收回给项目负责人；投资项目组成员仍可完成和提交计划。
- 不改变内核、投决、打款等阶段的审批顺序。
- 不改写已经存在的审批请求、节点和审批记录。
- 不生成系统自动通过的虚假审批单。
- 不直接修改生产业务数据；策略发布通过版本化 migration 完成。

## 方案比较

### 方案 A：恢复 `立项: ['boss']`（采用）

在默认策略和新版数据库策略中恢复老板节点，复用现有 `boss` 解析逻辑，将项目董事长和总裁合并为或签节点。

优点：符合用户确认的真实业务规则；复用现有审批引擎；审批记录、待办和审计语义一致。缺点：需要发布新策略版本并更新项目策略绑定。

### 方案 B：仅在服务端硬编码补一个老板节点

发现“立项”为空时临时生成老板节点。

优点：改动少。缺点：数据库政策、默认契约和运行行为不一致，管理页面仍显示错误规则，后续难以审计。

### 方案 C：保持无需审批并直接推进

优点：流程短。缺点：与用户明确确认的业务规则冲突，不采用。

## 详细设计

### 策略契约

将 `fdeWorkflowPolicyContract.ts` 的基线职责恢复为：

```ts
立项: ['boss']
```

Schema 校验继续保证已发布投资流程不得移除或重排该职责。默认节点名称为“董事长/总裁审批 · 立项”，模式为“或签”。

### 数据库策略版本

新增顺序递增的 migration：

1. 创建新的 FDE 工作流策略版本，内容与更新后的默认契约一致。
2. 将投资流程政策的活动版本指向新版本。
3. 将现有 `workflow_model='fde-v1'` 的活动投资项目绑定到新策略版本。
4. 不更新 `oa_approval_requests`、`oa_approval_nodes` 或历史审批记录。
5. migration 必须幂等并遵循现有迁移命名、登记和完整性规则。

### 审批节点解析

发起“立项 → 尽调计划制定”时，`resolveFdeApprovalNodes` 读取 `boss` 定义，并：

- 优先读取项目治理中的 `chairman`、`president` 职责绑定；
- 按现有稳定角色代码执行允许的回退；
- 只保留启用且资格有效的账号；
- 排除申请人本人；
- 合并、去重为一个“董事长/总裁审批”或签节点；
- 无有效审批人时返回 `FDE_APPROVER_NOT_CONFIGURED` 或现有更具体错误。

### 空节点防御

即使策略数据未来异常，`createOaApprovalRequest` 也不得直接读取空数组首项。创建审批请求前显式检查：

```text
如果 resolvedNodes 为空：
返回 409 OA_APPROVAL_NODES_REQUIRED，提示当前阶段未配置审批节点；
不创建审批请求、不修改项目阶段、不生成待办。
```

该防御是故障隔离，不替代正确的策略配置。

### 前端行为

- 项目中心保留“发起阶段审批”入口。
- 打开审批中心时展示“立项 → 尽调计划制定：董事长/总裁审批（任意一人）”。
- 提交成功后打开新审批详情并显示当前老板审批节点。
- 配置缺失时直接展示服务端业务错误，例如“请先配置当前项目的启用职责人员：董事长/总裁审批；申请人不可兼任审批人”。
- 只有未知网络错误或真正的服务不可达才显示“服务不可用”。

## 数据流

1. 黄昕在项目中心对处于“立项”的项目发起阶段审批。
2. API 校验黄昕是项目负责人、项目活动且目标为合法下一阶段。
3. 服务端读取项目绑定的新版已发布策略，得到 `boss` 节点。
4. 服务端解析项目董事长/总裁，排除申请人并冻结审批人快照。
5. 同一事务创建审批请求、发起人节点、老板审批节点、审批记录、待办和审计记录。
6. 项目保持“立项”，直到任一有效老板审批通过。
7. 审批通过后项目进入“尽调计划制定”，关闭同节点其余待办并记录阶段时间线。

## 错误与并发

- 项目已存在进行中的阶段审批时拒绝重复发起。
- 项目阶段或版本变化时返回状态冲突。
- 缺少有效审批人时不产生半成品审批数据。
- 同一老板节点多人或签时，首位有效审批人通过即完成节点；重复操作返回冲突。
- 创建和审批都在数据库事务中执行，失败整体回滚。
- 已发起审批始终使用持久化快照，不因后续人员或政策变化被静默改写。

## 测试设计

### 策略契约测试

- 默认策略中“立项”的职责为 `boss`，模式为“或签”。
- 删除或更改该节点时 Schema 校验失败。
- 其他阶段职责顺序保持不变。

### 节点解析测试

- 仅配置董事长时可生成老板节点。
- 仅配置总裁时可生成老板节点。
- 两者均配置时合并为同一或签节点。
- 申请人为其中一人时排除本人，另一人仍可审批。
- 排除申请人后无人可审批时返回明确配置错误。

### OA 服务验收

- “立项 → 尽调计划制定”成功创建审批请求和老板节点。
- 创建后项目仍处于“立项”。
- 任一有效老板通过后项目进入“尽调计划制定”。
- 同节点其他待办被关闭。
- 缺少审批人时返回 409 且数据库无审批半成品。
- 人为构造空节点策略时返回稳定 409，不出现 TypeError/500。
- 历史审批快照不因新策略发布变化。

### 前端测试

- 审批链展示该阶段老板审批。
- 项目中心入口提交后打开正确审批详情。
- 409 配置错误显示具体信息。
- 不再把本缺陷显示为笼统“服务不可用”。

## 验收标准

- 黄昕可以对“立项”项目成功发起进入“尽调计划制定”的审批。
- 新审批当前节点为“董事长/总裁审批”，并包含项目配置的有效审批人。
- 审批前项目不提前变更阶段；老板通过后才进入“尽调计划制定”。
- 接口不再返回 `Cannot read properties of undefined (reading 'id')`。
- 缺少审批配置时返回可理解的 409 业务错误。
- 相关测试、类型检查、平台门禁和生产构建通过。
