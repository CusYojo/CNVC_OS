# FDE 无审批节点阶段推进设计

日期：2026-09-15

状态：已确认

## 背景

FDE 投资流程将“立项 → 尽调计划制定”定义为无需审批的阶段转换。当前项目审批入口仍调用 `POST /api/oa/requests`，后端解析到空审批节点数组后继续读取首节点 `id`，导致 `TypeError` 和 HTTP 500，前端显示“服务不可用”。

## 目标

- 无审批节点的合法阶段转换直接生效，不创建虚假的 OA 审批实例。
- 在同一数据库事务中更新项目阶段、进度、阶段日期、工作流日志和审计记录。
- 有审批节点的阶段继续沿用现有 OA 审批流程。
- 非法的空节点配置不得再产生未捕获异常或 HTTP 500。
- API 返回结果能让现有前端刷新项目状态，并向用户展示准确反馈。

## 非目标

- 不修改已发布的 FDE 审批职责配置。
- 不为“立项 → 尽调计划制定”新增董事长、总裁或其他审批人。
- 不创建“系统自动通过”的审批实例。
- 不迁移或删除历史审批记录。
- 不调整其他阶段的材料、人员或审批规则。

## 方案比较

### 方案 A：直接推进阶段（采用）

当合法 FDE 阶段的审批节点数组为空时，服务端直接完成阶段转换并记录业务事实。

优点：符合当前流程规则；不伪造审批行为；用户操作路径最短。缺点：创建审批接口会出现两种成功结果，需要明确返回契约。

### 方案 B：创建自动通过审批单

创建只有“发起人提交”节点的已通过审批单，再推进项目。

优点：所有阶段都有审批单。缺点：把无需审批描述成审批通过，审计语义不准确，统计也会被污染。

### 方案 C：给该阶段增加审批节点

修改 FDE 工作流政策，使该转换继续进入人工审批。

优点：无需改变审批创建流程。缺点：改变已确认的业务制度，与“项目组直接制定计划”冲突。

## 详细设计

### 服务端分支

`createOaApprovalRequest` 在完成项目、申请人、生命周期、阶段、材料和权限校验，并解析审批节点后执行分支：

1. `resolvedNodes.length > 0`：保持现有审批单、审批节点、待办、通知和审计创建流程。
2. `resolvedNodes.length === 0`：仅允许已发布 FDE 政策明确配置为空节点的合法阶段；在当前事务内直接推进项目。

空节点直接推进必须完成：

- 使用项目当前版本/行锁保证并发安全；
- 更新 `projects.stage`、`projects.progress`、`projects.version` 和 `updatedAt`；
- 更新或创建对应的阶段日期事实；
- 写入项目工作流日志，来源明确标记为规则直接推进；
- 写入审计日志，记录申请人、项目、起止阶段和原因；
- 不写入 `oa_approval_requests`、`oa_approval_nodes`、审批待办或审批通知；
- 返回包含已更新项目和“无需审批、阶段已推进”语义的成功结果。

如果空节点并非来自已发布 FDE 政策，或者阶段不允许直接推进，服务端返回稳定的 409 业务错误，不得访问不存在的首节点。

### API 契约

保持 `POST /api/oa/requests` 入口兼容，成功结果使用可区分联合语义：

- `mode: "approval"`：返回新建的审批实例；
- `mode: "direct_transition"`：返回更新后的项目、起止阶段和用户提示。

若现有前端/共享类型不适合一次扩展联合返回，可在保持现有审批返回不变的前提下，为直接推进结果增加明确判别字段。禁止用伪审批对象填充既有类型。

### 前端行为

- 用户仍从项目中心点击当前的阶段操作入口。
- 收到 `approval` 结果时，继续打开新建审批详情。
- 收到 `direct_transition` 结果时，关闭提交弹窗，刷新项目域数据，并提示“该阶段无需审批，项目已进入尽调计划制定”。
- 不切换到“待我审批”，因为没有生成审批事项。
- 项目详情和阶段轨道应立即显示新阶段。

### 错误处理

- 对审批节点数组建立显式空值分支，禁止继续读取 `approvalNodes[0]`。
- 非法流程状态返回现有统一 JSON 错误合同和 Request ID。
- 直接推进事务任一步失败时整体回滚，项目阶段和日志不得部分写入。

## 数据流

1. 黄昕在项目中心发起下一阶段操作。
2. API 校验黄昕为项目负责人、项目处于活动状态且目标为合法下一阶段。
3. 服务端读取项目绑定的已发布 FDE 政策。
4. 政策确认当前阶段审批节点为空。
5. 同一事务内直接更新项目阶段及相关时间线、审计事实。
6. API 返回 `direct_transition`。
7. 前端刷新项目并显示直接推进成功提示。

## 测试设计

### 单元/契约测试

- FDE “立项 → 尽调计划制定”的政策解析结果为空节点。
- 空节点结果不会访问首审批节点。
- 有审批节点阶段仍返回审批模式。
- 未发布或非法空节点配置返回稳定 409。

### 服务端验收

- 负责人提交合法无审批阶段后项目阶段和进度正确更新。
- 不产生 OA 请求、审批节点、审批待办和审批通知。
- 工作流日志、阶段日期和审计记录完整。
- 重复提交因项目阶段已经变化而失败，不会重复推进。
- 事务中模拟失败时所有写入回滚。

### 前端测试

- 直接推进结果刷新项目并显示准确提示。
- 不打开审批详情、不切换“待我审批”。
- 普通审批结果保持原行为。
- 409/403 等业务错误显示服务端消息，而非笼统“服务不可用”。

## 验收标准

- 黄昕账号从处于“立项”的 FDE 项目发起下一阶段操作后，项目进入“尽调计划制定”。
- 页面不再显示“服务不可用”。
- 数据库中没有为该动作生成虚假审批实例。
- 时间线和审计记录可以追溯本次直接推进。
- 有人工审批节点的阶段不受影响。
- 相关测试、类型检查和定向验收通过。
